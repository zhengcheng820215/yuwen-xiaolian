# Phase 17 训练任务组 AI 规划契约

英文名称：Training Task Group AI Planning Contract

状态：P1 ENGINEERING IMPLEMENTED / V1.3 QUANTITY AND CONTEXT ENGINEERING IMPLEMENTED / DEBUG ACCEPTED / REAL ACCEPTANCE PENDING
契约版本：`training_task_group_ai_planning_contract_v1.3`
更新日期：2026-08-03

## 一、用途

本文定义素材资源录入平台中两项任务组级 AI 能力：

1. `重新规划候选任务组`：当前整组候选方向不合适时，生成一组替代方案；
2. `补充生成候选任务`：当前任务组基本可用但覆盖不足时，在保留已有任务的前提下补充候选任务。

两项能力只处理候选训练任务，不直接创建正式题目，不替代人工校准、质量检查、人工审核或发布。

本文与 [单训练任务重新生成契约](./SINGLE_TRAINING_TASK_REGENERATION_CONTRACT.md) 共同形成三个清晰作用域：

```text
单个任务表达不合适
-> 重新生成此任务

当前任务组可用，但覆盖不足
-> 补充生成候选任务

当前整组方向不合适
-> 重新规划候选任务组
```

## 二、核心对象与状态边界

### 2.1 任务状态

任务组级 AI 操作必须区分以下状态：

| 状态 | 含义 | 可否被重新规划替换 |
| --- | --- | --- |
| `candidate` | AI 生成但尚未人工确认的候选任务 | 可以 |
| `confirmed` | 已被人工采用并保存到当前工作草稿 | 不可静默替换 |
| `pending_review` | 已进入人工审核 | 不可替换 |
| `reviewed` | 已完成人工审核 | 不可替换 |
| `published` | 已生成正式题目或进入正式资源 | 不可替换 |

若现有数据模型暂时没有独立 `candidate` 状态，工程实现必须使用独立候选容器，不得把候选直接写入当前 Plan Revision。

### 2.2 候选容器

任务组规划结果建议使用独立对象表达：

```ts
type TrainingTaskGroupCandidate = {
  candidateGroupId: string;
  materialVersionId: string;
  planId: string;
  basedOnPlanRevision: number;
  operationType: 'replace_group' | 'supplement_group';
  attemptId: string;
  createdAt: string;
  tasks: TrainingTaskCandidate[];
};
```

候选对象不是正式 `Material Observation Plan`，不能被审核页、发布页或 Runtime 当作当前资源。

补充生成还必须携带稳定的去重与覆盖上下文：

```ts
type SupplementGenerationContext = {
  materialVersionId: string;
  basedOnPlanRevision: number;
  existingTasks: ExistingTaskSummary[];
  existingObservationPoints: ObservationPointSummary[];
  existingAbilityIds: string[];
  remainingCoverageGaps: CoverageGap[];
  currentAcceptedTaskCount: number;
  maximumAcceptedTaskCount: 5;
};
```

`existingTasks` 不是只传题干文本。它至少包含当前任务组全部任务、尚未采用的候选，以及同一 Material Version 下仍可追溯的待审核或已发布兄弟任务；每项摘要必须保留材料锚点、回答对象、认知动作、观察目标、评分要点、能力和任务用途。停用或历史任务可以只作为重复提醒来源，不直接占用当前任务组数量上限。

### 2.3 本期人工创建边界

本契约不否定未来从空白人工创建训练任务的能力，但本期不提供“增加训练任务”或“从空白创建训练任务”入口。

本期用户只能：

1. 采用 AI 候选任务；
2. 重新生成已有单个任务；
3. 编辑并校准已有任务。

未来若增加人工创建入口，应放入“更多操作”或独立人工创建流程。人工创建结果直接写入当前编辑缓冲区，保存后进入当前工作草稿并按人工编辑规则重新触发检查；提交审核时才冻结为新 Revision。人工创建任务不得标记为 AI 生成，也不得写入 `TrainingTaskGroupCandidate`。

### 2.4 候选采用的最小单位

采用粒度按操作类型冻结：

| 操作类型 | 采用单位 | 采用后行为 |
| --- | --- | --- |
| `replace_group` | 整组采用 | 用完整替代组更新编辑缓冲区中的可替换任务 |
| `supplement_group` | 逐项采用 | 只把人工勾选的补充候选加入编辑缓冲区 |

`replace_group` 不允许部分采用，以免破坏 AI 给出的整体覆盖结构；`supplement_group` 不要求整组采用，以免用户为了补一个缺口被迫接受无关任务。两类采用都不直接创建 Revision。

### 2.5 首次规划与整组替代的产品语义

当当前编辑缓冲区中的真实训练任务数为 `0` 时，AI 生成整组候选属于`首次规划`，不是`重新规划`或`整组替代`。

工程底层可以复用 `replace_group` 的整组候选生成与采用算法，但页面必须根据当前真实任务数投影正确语义：

| 当前真实任务数 | 产品模式 | 候选标题 | 次操作 | 主操作 |
| --- | --- | --- | --- | --- |
| `0` | 首次规划 | `首批候选训练任务` | `放弃候选` | `采用这组候选` |
| `> 0` | 整组替代 | `替代候选任务组` | `保留当前任务组` | `用候选组替换当前任务组` |

首次规划模式必须遵守以下规则：

1. 不展示“当前任务组与替代方案”比较，因为当前不存在可比较的任务组；
2. 不显示“保留当前任务组”，因为空集合不是一个可保留方案；
3. 不使用“替换”描述采用行为，采用只表示把首批候选加入编辑缓冲区；
4. 放弃候选后继续保持 `0` 个任务，并回到 AI 规划入口；
5. 采用候选仍不创建 Revision，只有保存任务组才创建或更新当前工作草稿；
6. 空白 UI 占位项不得计入当前真实任务数，也不得把首次规划误判为整组替代。

### 2.6 任务数量建议与质量优先级

首次规划的任务数量是 AI 基于材料形成的规划结论，不是用户必须完成的固定目标。首次规划结果必须同时返回数量建议和理由：

```ts
type InitialTaskCountRecommendation = {
  recommendedTaskCount: 2 | 3;
  recommendationReason: string;
  supportedObservationPoints: Array<{
    abilityId: string;
    trainingDirection: string;
    materialAnchor: string;
  }>;
};
```

页面应展示“建议训练任务：3 个”及其材料支持、能力覆盖和观察方向，不得使用“生成 3 条”暗示系统只能生成固定数量。能力与观察方向必须分开展示，不得把“信息提取、人物、主题”等不同维度混为同一组标签。

首次规划与补充生成统一遵守以下数量边界：

1. 首次规划由 AI 在 `2—3` 条范围内给出推荐数量；`3` 条是常见推荐，不是固定目标；
2. 材料只支持 `2` 条独立且有价值的观察任务时，必须返回 `2` 条并说明未继续生成的原因，不得以近义改写补足第三条；
3. 补充生成根据明确覆盖缺口返回 `1—2` 条候选，实际数量不得超过 `5 - currentAcceptedTaskCount`；`1—2` 只是容量边界，不是要求补足的数量；
4. 当前已采用任务为 `4` 条时最多补充 `1` 条；达到 `5` 条时禁用补充入口并说明应先处理现有任务；
5. 未采用候选不直接计入已采用任务总数，但必须进入重复判断，且页面不得允许用户采用后超过 `5` 条；
6. 当前任务组建议容量为 `2—5` 条。数量范围只约束单轮当前任务组，不限制同一 Material Version 的历史正式资源数量。

AI 的取舍优先级冻结为：

```text
材料依据
>
观察价值与差异
>
能力覆盖
>
任务数量
```

用户明确选择某项缺失能力时，该能力可以成为本次生成约束，但仍不得越过材料依据和观察价值。首次规划回答“当前材料适合形成几个独立观察任务，以及为什么”；补充生成回答“当前覆盖缺少什么，以及能否形成新的独立观察”，不得回答“再生成几个”。

## 三、重新规划候选任务组

### 3.1 适用场景

用于以下情况：

1. 当前候选任务过度集中在单一能力或训练方向；
2. 整组任务与材料特点不匹配；
3. 用户希望重新获得一套覆盖结构，而不是逐题修补；
4. 当前任务均未确认、未送审且未发布。

### 3.2 数据行为

```text
当前未确认候选任务组 A
-> AI 生成候选任务组 B
-> 用户比较 A 与 B
-> 采用 B 或保留 A
```

规则：

1. 点击入口只生成替代候选，不立即删除当前候选；
2. `replace_group` 默认按整组采用，不支持从替代候选组中只挑选部分任务；
3. 用户采用新方案后，先以整组新候选替换当前编辑缓冲区中的未确认候选；
4. 已确认、待审核、已审核和已发布任务不参与替换；
5. 若当前任务组混合了候选任务和受保护任务，只能整组替换候选部分；
6. AI 失败、返回空结果或未形成有效差异时，继续保留原候选任务组；
7. 采用新任务组只更新编辑缓冲区并标记未保存，不立即创建 Plan Revision；
8. 未采用、关闭比较区或取消操作不修改编辑缓冲区，也不创建 Revision。

### 3.3 操作确认

执行前必须明确影响范围：

> 将重新规划当前未确认的 4 个候选任务。已确认、已审核和已发布任务不受影响。新方案生成后可与当前方案比较，再决定是否采用。

操作：

- `继续重新规划`
- `取消`

不得使用“重新生成全部任务”等容易误解为覆盖正式任务的文案。

## 四、补充生成候选任务

### 4.1 适用场景

用于以下情况：

1. 当前任务组总体可用，但缺少一个能力或训练方向；
2. 当前观察覆盖存在能够被材料支持的明确缺口；
3. 覆盖检查指出明确缺口；
4. 用户希望保留已有任务，仅增加新的候选。

### 4.2 数据行为

```text
当前任务组
├─ 已有任务 1
├─ 已有任务 2
└─ 已有任务 3

补充生成
-> 新增候选任务 4
```

规则：

1. 现有任务保持不变；
2. AI 只能新增候选，不得修改兄弟任务；
3. 新候选允许逐项采用，采用后先写入当前编辑缓冲区；
4. 未采用的候选不进入审核和发布；
5. 新候选不得复用已有任务的逻辑身份或题号；
6. AI 无法生成明显不同的任务时，不得用近义改写凑数；
7. 达到任务数量上限时入口禁用，并解释原因。

### 4.3 生成输入

AI 必须读取：

1. 当前 Material Version 与可用材料范围；
2. 当前任务组的能力、训练方向、题目、学生任务、观察目标和评分要点；
3. 当前覆盖摘要与明确的 `remainingCoverageGaps`；
4. 用户选择的补充方向；
5. 已存在但尚未采用的候选，避免重复生成；
6. 同一 Material Version 下待审核、已确认或已发布兄弟任务的去重摘要；
7. 当前已采用任务数、剩余可采用名额和本次允许返回的最大候选数。

用户可选补充方向：

- 训练能力；
- 训练方向；
- 任务用途。

这些输入用于限制候选，不得直接覆盖当前 Plan 的受控字段。

补充候选数量由覆盖缺口、材料支持和剩余可采用名额共同决定，不作为用户选择项。页面不得使用“任务不够”“再加几个”或“添加更多任务”解释补充生成。

补充请求缺少上述已有任务上下文、覆盖缺口或剩余名额时，Application Service 必须拒绝调用 Provider，不得退化为无上下文的“再生成几个任务”。

### 4.4 无有效增量

当 AI 判断没有明显覆盖缺口，或候选与现有任务高度重复时，应返回：

> 当前任务组覆盖较完整，暂未生成具有明显差异的新任务。可以调整补充方向后重试。

此结果不创建候选任务，不创建 Plan Revision。

## 五、AI 生成约束

### 5.1 共同约束

两类任务组操作都必须：

1. 遵守 [Phase 17 录入字段契约](./AUTHORING_FIELD_CONTRACT.md)；
2. 使用稳定 `abilityId`，不得把自由文本能力名称直接写入正式字段；
3. 保持题目、学生任务和观察目标的职责分离；
4. 保持 Material Version、Plan 和材料范围的可追溯关系；
5. 输出逐任务的差异说明与覆盖贡献；
6. 标记 AI 无法可靠决定、需要人工确认的字段。

### 5.2 去重判断

不得只比较能力标签或题干文本。候选与现有任务至少比较：

1. 学生回答的对象是否相同；
2. 使用的材料范围与证据是否相同；
3. 要执行的认知动作是否相同；
4. 评分时检查的答案要点是否相同；
5. 任务用途是否相同。

能力或问法相同本身不构成重复。只有考查对象、材料依据和评分要点高度重合时，才应判定为重复候选。

去重集合必须覆盖当前任务、未采用候选与同一 Material Version 下可追溯的待审核或已发布兄弟任务。仅比较本轮当前任务会遗漏跨轮重复，不能满足补充生成契约。

### 5.3 覆盖贡献

补充候选必须说明新增价值：

```ts
type CandidateCoverageContribution = {
  abilityId: string;
  trainingDirection: string;
  taskRole: string;
  coverageReason: string;
  differsFromTaskIds: string[];
};
```

无法说明新增价值的候选不得进入人工采用区。

## 六、版本、Assessment 与审核

### 6.1 工作草稿与 Revision 创建规则

候选采用与持久化必须分离：

```text
采用候选
-> 写入当前编辑缓冲区
-> 标记任务组存在未保存修改
-> 保存任务组并重新检查
-> 更新当前唯一工作草稿
-> 旧 Assessment 失效
-> 提交人工审核
-> 冻结为新的 Plan Revision
```

每个 `Material + Plan` 在同一轮未提交修改中只能存在一个可变工作草稿。工作草稿不是历史版本节点，不得因反复保存而连续生成“第 2 版、第 3 版”等未提交 Revision。

规则：

1. 首次产生有效修改时创建工作草稿；
2. 后续执行`保存任务组并重新检查`时更新同一个工作草稿，不新增 Plan Revision；
3. 内容没有变化时不执行持久化写入，也不重新生成检查结果；
4. 用户执行`提交题目审核`时，才把当前已保存且检查有效的工作草稿冻结为一个新的 Plan Revision；
5. 审核退回后继续修改该修订稿，不因返回编辑、保存或重新检查而新增 Revision；
6. 再次提交审核时更新该修订稿的审核状态，不重复生成内容相同的 Revision；
7. 已审核、已发布和历史 Revision 均不可覆盖；
8. 只有在上一 Revision 已成为不可变历史节点，且用户开始新一轮实质修改时，才允许建立新的工作草稿。

版本选择器默认只展示：

1. 当前工作草稿，统一标记为`工作草稿 · 未提交审核`；
2. 已提交审核、审核通过、已发布或被历史引用的不可变 Revision。

被同一工作草稿覆盖的中间保存记录不得作为独立版本展示。

以下操作不创建 Revision：

1. 发起生成；
2. AI 重试；
3. 查看候选；
4. 放弃候选；
5. AI 生成失败；
6. 候选与现有内容没有有效差异；
7. 将候选采用到编辑缓冲区；
8. 保存或重新检查当前工作草稿；
9. 重复点击保存且内容没有变化；
10. 审核退回后继续修改同一修订稿。

### 6.1.1 任务删除规则

删除属于任务组编辑，不依赖单任务是否已进入`编辑并校准`状态。

1. 当前编辑缓冲区内的任务数大于 3 时，删除入口可直接使用；
2. 任务组必须至少保留 3 个任务；达到下限后删除入口禁用，并明确提示“每个训练任务组至少保留 3 个任务”；
3. 删除只从当前编辑缓冲区移除任务并标记未保存，不改写当前 Revision、历史 Revision 或已发布 Question Resource；
4. 删除、候选采用和其他人工编辑可以连续发生；执行`保存任务组并重新检查`时只更新当前工作草稿，不新增 Plan Revision；
5. 保存前允许撤销删除；撤销后恢复原任务身份与内容，不创建 Revision；
6. 删除已审核或已发布任务时，实际含义是在当前工作草稿中不再采用该任务；提交审核后形成的新 Revision 才记录这一差异，历史版本与正式资源继续保留并可追溯。

### 6.2 Assessment 失效

保存已采用候选属于影响正式质量判断的编辑操作：

1. 当前工作草稿不得沿用修改前的 Validation；
2. 被替换或新增任务必须重新执行结构与质量检查；
3. 工作草稿的人工审核状态恢复为待检查；
4. 已发布任务绑定的旧 Revision 与 Assessment 保持有效，不被覆盖；
5. 旧 Revision、旧 Assessment 和旧 Review 继续保留用于追溯。

候选刚写入编辑缓冲区但尚未保存时，页面必须显示“任务组存在未保存修改”，审核与发布入口不可用。

### 6.3 保护正式内容

任何任务组级操作都不得：

1. 删除已发布 Question Resource；
2. 改写已审核任务的历史 Revision；
3. 让候选任务直接进入 Registry 或 Runtime；
4. 让新候选复用已有正式题目的资源 ID；
5. 因重新规划而重新生成兄弟任务的待审核草稿。

## 七、幂等、并发与失败恢复

### 7.1 幂等键

每次人工发起生成必须具有稳定 `attemptId`：

```text
同一 attemptId 的网络重试
-> 返回同一候选结果

用户主动再次生成
-> 创建新的 attemptId
```

重复回调不得创建重复候选或重复 Plan Revision。

### 7.2 并发保护

生成期间：

1. 同一 Material + Plan 只允许一个任务组级生成操作；
2. 单任务重新生成可与任务组操作互斥；
3. 当前 Plan Revision 发生变化后，旧候选标记为过期，不能采用；
4. 采用时必须再次校验 `basedOnPlanRevision`。

### 7.3 失败恢复

生成失败时：

1. 原任务与原候选组继续保留；
2. 页面说明失败原因和可重试动作；
3. 不创建空任务组；
4. 不改变当前审核或发布状态；
5. 不自动重复请求，除非属于明确的可恢复网络重试。

## 八、交互与布局

### 8.1 入口层级

入口放在“当前训练任务覆盖”模块，不放进单张任务卡：

```text
当前训练任务覆盖
能力：理解 / 分析 / 推理
方向：人物 / 情节 / 主题

[补充生成候选任务]  [重新规划候选任务组]
```

推荐层级：

1. `补充生成候选任务`：主要入口；
2. `重新规划候选任务组`：次级入口；
3. 单卡片保留 `重新生成此任务` 与 `编辑并校准`。

两项任务组入口均属于 AI 操作，使用产品定义的紫色 AI 按钮语义；采用 AI 候选和校准 AI 预览仍处于 AI 结果处理阶段，可以使用紫色并通过文案明确其人工决策属性。候选进入普通编辑缓冲区后，保存、检查、审核和其他人工编辑恢复各自的常规动作或状态颜色。

### 8.2 候选展示

首次规划必须展示：

- `首批候选训练任务`；
- AI 推荐的任务数量及推荐理由；
- 分开展示的能力覆盖与观察方向；
- 候选任务内容与覆盖摘要；
- `采用这组候选`与`放弃候选`；
- 采用后进入编辑缓冲区、保存前不创建版本的说明。

首次规划不得展示空的当前任务组、替代覆盖比较、`保留当前任务组`或任何“替换现有任务”的说明。

重新规划必须展示：

- 当前任务组；
- 新候选任务组；
- 能力和训练方向覆盖变化；
- 被保护、不受影响的任务；
- 重复检查结果。

补充生成必须展示：

- 当前覆盖缺口；
- 新增候选任务；
- 每项候选的新增价值；
- 与已有任务的差异；
- `采用所选候选`与`放弃候选`。

补充生成入口统一使用 `补充生成候选任务`。禁止使用 `添加更多任务`、`补充更多任务` 或其他以数量增长为中心的文案。

### 8.3 页面动作分区

页面动作按职责固定为五个区域，不得在同一位置重复表达：

1. 任务组覆盖区：`补充生成候选任务`、`重新规划候选任务组`；
2. 单任务卡片：`重新生成此任务`、`编辑并校准`、`删除`；
3. 候选比较区：
   - 首次规划：`采用这组候选`、`放弃候选`；
   - `replace_group`：`用候选组替换当前任务组`、`保留当前任务组`；
   - `supplement_group`：`采用所选候选`、`放弃候选`；
4. 编辑区底部：`保存任务组并重新检查`；
5. 审核区：`返回任务调整`、`提交题目审核`。

`保留当前任务组`只用于存在真实当前任务的整组替换比较；`放弃候选`用于首次规划或补充候选。首次规划不得出现保留或替换动作。

### 8.4 操作文案

统一使用：

- `重新规划候选任务组`
- `补充生成候选任务`
- `重新生成此任务`
- `编辑并校准`
- `用候选组替换当前任务组`
- `采用所选候选`
- `保留当前任务组`
- `放弃候选`
- `保存任务组并重新检查`
- `返回任务调整`
- `提交题目审核`

禁止使用：

- `增加训练任务`
- `重新生成全部`
- `覆盖当前任务`
- `直接发布`

### 8.5 未规划态与检查启动边界

保存 Material 只表示素材版本已经建立，不表示训练任务或 Material Observation Plan 已经存在。素材已保存但尚未执行 AI 规划时，页面必须保持合法的“未规划”状态：

1. 训练任务集合为 `0`，不得创建空白占位任务或把 UI 模板计入任务总数；
2. 首层只展示“规划训练任务”及 AI 规划入口，不展示训练任务质量提醒、“去修改”或可进入审核结论；
3. 训练任务检查、覆盖统计和问题定位只有在真实任务已经由 AI 生成并被人工采用，或从有效 Plan 恢复后才能启动；
4. `savePlanRevision` 在任务数为 `0` 时必须拒绝执行，并明确提示先完成 AI 规划和候选采用；
5. 空状态不得生成 Validation、Assessment、Review、Question Draft 或 Plan Revision；
6. 页面可以展示素材自身的保存结果和素材级信息，但不得把“素材已保存”投影为“任务待修改”。

这条边界用于防止初始化占位数据越过正式任务身份：检查系统只能消费真实业务对象，不能消费为了布局或表单初始化而构造的临时 UI 数据。

### 9.1 页面 Command 对齐

录入平台必须使用下列独立 Command，不得让多个按钮复用一个无法区分作用域的通用生成或保存 handler：

| Command | 唯一职责 | 数据写入 |
| --- | --- | --- |
| `regenerateSingleTask` | 为当前任务生成一个替代候选 | 只写单任务候选状态 |
| `planSupplementCandidates` | 根据覆盖缺口生成补充候选 | 只写任务组候选状态 |
| `planReplacementGroup` | 生成完整替代候选组 | 只写任务组候选状态 |
| `adoptCandidates` | 把人工选中的候选采用到编辑缓冲区 | 只写当前编辑缓冲区 |
| `savePlanRevision` | 保存当前编辑缓冲区 | 创建或更新当前唯一工作草稿，不新增历史 Revision |
| `runPlanValidation` | 对已保存工作草稿执行检查 | 写入该工作草稿的 Validation |
| `submitForQuestionReview` | 提交已保存且检查有效的工作草稿 | 冻结一个 Plan Revision，并创建或更新审核记录 |

当前后端服务会在 `savePlanRevision` 成功后原子执行 `runPlanValidation`。这是同一次服务事务中的两个明确阶段，不代表页面可以绕过保存直接检查未保存内容，也不代表每次保存都应创建 Revision。

所有 Command 的可用性必须由统一状态门禁决定，至少包括：

- 是否已选择素材；
- 是否已有可编辑 Plan；
- AI 服务是否可用；
- 是否存在未保存修改；
- 是否已有候选；
- 当前任务数是否达到上限；
- 当前 Revision 的检查是否有效；
- 是否满足提交审核条件。

按钮禁用状态、点击后的保护和提示文案必须读取同一门禁结果，避免出现“按钮看似可用，点击后才发现不能执行”的错位。

### 9.2 P1 数据写入边界

P1 必须保持以下边界：

```text
AI 生成候选
-> Candidate Session
-> 人工逐项采用
-> 当前编辑缓冲区（dirty）
-> 保存任务组并重新检查
-> 创建或更新唯一工作草稿
-> 对该工作草稿执行检查
-> 提交题目审核
-> 冻结为一个新 Plan Revision
```

以下行为不得创建 Revision：

- 打开或关闭候选比较区；
- 生成补充候选；
- 生成失败；
- 勾选或取消勾选候选；
- 放弃候选；
- 将候选采用到尚未保存的编辑缓冲区。

只有 `savePlanRevision` 可以创建或更新工作草稿，只有 `submitForQuestionReview` 可以把工作草稿冻结为 Plan Revision。存在未保存修改时，AI 规划、再次采用候选和提交审核均应被统一门禁阻止。

## 十一、验收标准

1. 单任务、补充生成和整组重新规划三个入口作用域清晰；
2. 补充生成保留所有现有任务，只增加未确认候选；
3. 补充候选可以逐项采用；
4. 重新规划必须整组采用，只替换未确认候选，不影响受保护任务；
5. 本期页面不存在“增加训练任务”或空白人工创建入口；
6. 查看、放弃、生成失败或采用到编辑缓冲区均不创建 Plan Revision；
7. 采用候选后页面显示未保存状态，审核与发布入口不可用；
8. 同一轮修改首次保存只建立一个工作草稿，后续保存持续更新该草稿，不新增 Plan Revision；
9. 保存后当前工作草稿的 Validation 重新执行，旧 Review 和 Assessment 不得被当作当前结论；
10. 重复保存、反复编辑、删除后撤销或无变化内容均不产生重复 Revision；
11. 重复请求与重复回调不产生重复候选或重复 Revision；
12. Plan Revision 改变后旧候选不可采用；
13. 新候选不会直接进入审核、发布、Registry 或 Runtime；
14. 已审核任务的历史 Revision 与已发布 Question Resource 不会被覆盖或物理删除；
15. AI 无法形成明显差异时不以近义改写凑数；
16. 补充候选可说明新增覆盖价值；
17. 其他任务旧 Revision、正式题目与历史 Assessment 保持不变；
18. 整组替换与补充候选分别显示匹配的采用、保留或放弃动作；
19. 页面清楚说明本次会替换、保留或新增哪些任务；
20. 真实材料验收中不会出现重复草稿、任务身份错乱或题号重排；
21. 连续生成并采用多轮替代、补充候选时不新增 Revision；最终保存只更新一个工作草稿，并使此前候选失效；
22. 任务数大于 2 时，无须先进入单任务编辑状态即可删除任务；
23. 任务数为 2 时禁止继续删除，并显示最低数量原因；
24. 删除后未保存时，当前 Revision 与历史资源不变，页面显示任务组存在未保存修改；
25. 删除后撤销可恢复原任务，且不创建 Revision；
26. 连续删除、编辑和采用候选后，最终保存只更新当前工作草稿；
27. 同一轮未提交修改在版本选择器中只显示一个`工作草稿 · 未提交审核`；
28. 提交人工审核时才新增一个不可变 Plan Revision；
29. 审核退回后继续修改和重新检查同一修订稿，不新增重复 Revision；
30. 上一 Revision 已冻结后开始新一轮实质修改，才创建新的工作草稿；
31. 连续保存十次同一工作草稿后，版本列表中的历史 Revision 数量保持不变。
32. 仅保存 Material、尚未生成训练任务时，任务总数为 `0`，页面不显示任务质量提醒或“去修改”；
33. 空任务集合不能保存任务组、创建 Plan Revision 或进入题目审核；
34. 当前真实任务数为 `0` 时，首次生成只显示“首批候选训练任务 / 放弃候选 / 采用这组候选”，不显示“保留当前任务组”或替换语义；
35. 首次候选采用后只更新编辑缓冲区，放弃后继续保持空任务状态，两种操作均不创建 Revision；
36. 当前真实任务数大于 `0` 时，重新规划仍显示新旧覆盖比较以及整组保留或替换动作；
37. 首次规划由 AI 在 `2—3` 条范围内给出推荐，`3` 条只是常见建议；材料只支持 `2` 条独立任务时返回 `2` 条并说明原因；
38. 补充生成每次只返回 `1—2` 条，已有 `4` 条时最多返回 `1` 条，已有 `5` 条时入口禁用；
39. 补充请求包含当前任务、未采用候选和同一 Material Version 下待审核或已发布兄弟任务的去重上下文；
40. 缺少上下文、覆盖缺口或剩余名额时不调用 Provider；无有效增量时返回空候选且不创建 Revision；
41. 候选采用后不得超过 `5` 条，数量约束不覆盖历史正式资源；
42. 自动化与真实材料验收能够证明取舍顺序为“材料依据 > 观察价值与差异 > 能力覆盖 > 任务数量”。
43. 首次规划结果同时返回推荐数量、推荐理由和材料支持的独立观察点，页面不把推荐数量展示为固定系统限制；
44. 能力覆盖与观察方向分开展示，数量不作为补充方向供用户选择；
45. 补充入口和结果不使用“添加更多任务”“补充更多任务”或“再加几个”等数量导向文案。
46. AI 生成并采用真实任务后，任务检查才开始统计通过项、提醒项和阻断项；
47. 从已有有效 Plan 恢复时仍正常加载真实任务并执行检查，不受未规划空状态规则影响。

## 十三、任务级题目生命周期投影

训练任务组顶部只保留题目生命周期的数据总览，不再承担明细展开、题目查看或状态处理。
具体状态与操作必须归属到对应训练任务卡片，避免用户先操作汇总数字，再反向寻找任务。

顶部总览固定为只读统计：

1. 待人工审核；
2. 发布未完成；
3. 已发布。

顶部统计不得显示展开箭头，不得响应点击，也不得在下方生成题目明细列表。

每张训练任务卡必须同时区分两个维度：

1. 计划状态：是否已纳入当前训练计划；
2. 题目状态：该任务对应题目所处的草稿、审核或发布阶段。

两类状态不得合并成一个标签。题目状态通过稳定的 `observationTaskPlanId` 关联，不得使用题目标题、
题号或数组位置推断。状态优先级固定为：

```text
已发布
> 发布未完成
> 当前题目 Draft 状态
> 未生成题目
```

题目状态与动作映射如下：

| 题目状态 | 任务卡动作 |
| --- | --- |
| 未生成题目 | 不显示查看动作 |
| 草稿 / 需重新检查 / 退回修改 | 继续修改 |
| 待题目人工审核 | 查看审核 |
| 审核通过（待发布） | 查看发布准备 |
| 发布未完成 | 处理发布问题 |
| 已发布 | 查看正式资源 |

任务卡动作只打开当前任务对应的题目对象，不得打开无关题目或重新创建 Draft。若历史数据中同一任务
存在多个题目记录，页面只投影当前有效 Draft 或当前有效正式版本；历史记录留在追溯区，不参与当前
状态和顶部统计。

验收必须确认：

1. 顶部三个统计不可点击且没有展开箭头；
2. 页面不存在顶部统计对应的题目明细展开区；
3. 每张任务卡同时显示计划状态与题目状态；
4. 有关联题目的任务可从卡片进入正确题目；
5. 无关联题目的任务显示“未生成题目”，且不会创建空 Draft；
6. 同一任务从草稿、待审核、待发布到已发布时，卡片状态和动作随统一生命周期投影更新。
