# PC / 平板学习工作台体验校准记录

## 一、文档定位

本文记录 Phase 12 基础全链路集成完成后，PC / 平板连续学习工作台的体验校准结果。

本次校准不新增 Phase 编号，不改变 Phase 12 的冻结状态，也不增加新的教育判断能力。它只负责把已经成立的连续学习 Runtime，整理为学生能够专注阅读、自然作答和清楚理解状态的学习界面。

记录日期：2026-07-15  
文档版本：`PC / Tablet Learning Workspace UX Calibration v1`  
记录状态：`Accepted`
学生反馈语言增补：2026-07-21
反馈视觉细节增补：2026-07-21
平台布局与按钮规范增补：2026-07-26

## 二、核心体验目标

学习工作台应保持干净、清爽，以内容信息为中心搭建布局结构，最大程度让学生把注意力集中在阅读材料、题目和自己的回答上。

核心原则：

1. 内容优先于装饰。
2. 学习任务优先于产品说明。
3. 学生可读信息优先于 Runtime 状态。
4. 交互应干净利落，避免多余步骤和重复入口。
5. 色彩、图标、卡片和提示元素应保持克制。
6. 页面可以留白，但不能用装饰填充留白。
7. 每个可见元素都必须对当前学习行为有明确作用。

## 三、主要使用设备

第一版以 PC 和平板横屏为主要学习设备。

PC / 平板主要承担：

- 长文本阅读；
- 阅读理解与开放题作答；
- 较长答案输入；
- 连续多轮学习；
- 反馈阅读与答案修改。

移动端主要适合：

- 选择题；
- 判断题；
- 简短填空；
- 简短回答；
- 查看轻量学习状态。

移动端暂不作为长篇阅读、作文输入和复杂开放题的主要体验载体。

## 四、布局原则

### 1. PC 双栏工作台

PC 主工作区采用稳定双栏布局：

```text
左侧：阅读材料
右侧：本轮重点 / 题目 / 回答 / 反馈
```

布局要求：

- PC 与笔记本（`1280px` 及以上）按 `40% / 60%` 划分；
- Pad 横屏（`1024px–1279px`）按 `45% / 55%` 划分，优先保证阅读行宽；
- Pad 竖屏及更窄视口切换为上下结构，不继续压缩双栏；
- 工作区宽度随视口流动适配，并以 `1400px` 为最大宽度、`1200px` 为舒适基准；
- 不设置 `1200px` 最小宽度，空间不足时应继续收缩或切换为上下结构；
- 分栏背景、纵向分割线与内容区域必须使用同一响应式几何边界；
- 左右内容容器最大宽度均为 `640px`，分别在所属区域内水平居中；
- 右侧标题、题目、回答、反馈和下一步操作保持内部左对齐，并共用一致的左右边界；
- 顶栏横向贯通可用区域，不形成悬浮卡片；
- 左右内容区分别滚动时，不应遮挡题目或操作按钮；
- 阅读材料在作答过程中应尽量持续可见；
- 左右栏不通过装饰性卡片再次嵌套。

### 2. 平板适配

平板横屏优先保持双栏。

当可用宽度不足时，可以降低栏间距和内边距，但不能压缩到影响阅读行长、题目理解或答案输入。

平板竖屏可以切换为上下结构，但必须保持：

- 阅读材料在前；
- 阅读材料与学习任务使用相同的最大内容宽度和左侧对齐轴；
- 阅读材料区域底部使用浅灰分割线，明确上下模块关系；
- 题目和答案紧密相邻；
- 提交后能自然进入反馈；
- 不因响应式适配改变学习流程语义。

### 3. 学习平台统一宽度与排列规范

学习平台采用“统一外壳、按学习阶段选择排列方式”的布局，不把内部录入平台的纵向结构机械复制到作答场景：

- 学习入口顶栏内容最大宽度使用 `1360px`，与内部生产工作台保持统一的产品外壳；
- 学习入口主体最大宽度使用 `1200px`，采用纵向单栏组织状态、说明和主要操作；
- 正式作答工作区最大宽度继续使用 `1400px`，PC 与笔记本保留阅读材料和学习任务双栏，避免学生反复滚动查找上下文；
- `1280px` 及以上使用 `40% / 60%`，`1024px–1279px` 使用 `45% / 55%`；
- 小于 `1024px` 时切换为纵向排列，阅读材料在上、学习任务在下，并保持一致的内容宽度与左侧对齐轴；
- 反馈页、完成页和流程阻断页使用纵向单栏，主要内容最大宽度保持约 `720px`；
- 顶栏、入口、作答、反馈与完成页面使用一致的水平内边距、按钮字号、圆角和焦点规范；
- 响应式变化只调整宽度与排列方式，不改变任务、提交、反馈和下一步流程语义。

### 4. 内部生产工作台宽度规范

素材录入、题目审核和同类内部生产工作台采用统一的“宽顶栏、收敛主体”布局：

- 顶栏内容最大宽度使用 `1360px`，为返回入口、页面标题和批次级操作保留稳定空间；
- 主体内容最大宽度使用 `1200px`，控制材料阅读行长和长表单的横向跨度；
- 顶栏与主体分别水平居中，不要求左右边缘完全重合；
- 不设置 `1200px` 最小宽度；在笔记本和平板视口下按可用宽度流动收缩；
- 主体在窄视口下保留必要水平内边距，不产生横向滚动；
- PC、笔记本和平板只改变可用宽度和必要的排列方式，不改变录入、审核和发布流程语义；
- 单个页面不得自行新增 `1120px`、`1280px` 或“主体与顶栏同宽”等平行口径，确需例外时必须在对应 UX 文档中说明原因。

## 五、字号与文本层级

第一版只使用三档主要字号：

| 字号 | 使用范围 |
| --- | --- |
| `14px` | 辅助说明、状态信息、按钮文字 |
| `16px` | 阅读材料、题目、答案输入、反馈正文 |
| `18px` | 区域标题、本轮重点、主要结果标题 |

原则：

- 不使用过多字号制造层级；
- 阅读材料默认使用 `16px`，避免在 PC 上显得过大；
- 按钮文字统一使用 `14px / 400`，不通过加粗制造操作层级；
- 行高应支持持续阅读，正文建议保持约 `1.7`；
- 不使用负字距；
- 不随视口宽度连续缩放字号。

## 六、色彩与视觉元素

视觉表达应服务于信息层级，不承担装饰任务。

颜色、状态、操作与 AI 身份的最终语义遵循 [产品颜色语义规范](./PRODUCT_COLOR_SEMANTICS.md)。本 UX 文档只描述页面体验，不另行定义按钮颜色体系。

要求：

- 页面以白色和浅灰背景为主；
- 学习工作区与轮次过渡页的浅灰底统一使用 `#f7f9fc`；
- 蓝色只用于当前状态、可操作焦点和必要强调；
- 绿色用于完成或保存成功；
- 红色只用于明确阻断和错误；
- 常规主要操作使用深蓝实心按钮，常规次要操作使用白底深蓝描边；AI 操作使用紫色，危险操作使用红色；
- 常规按钮的 Hover 与 Focus 延续蓝色操作语义；输入组件聚焦态统一使用蓝色焦点环；
- 绿色只表达完成、通过、成功或可用结果，不承担普通流程操作；
- 禁用状态使用中性灰色，并通过文字说明不可用原因；
- 返回、关闭和 Toast 关闭等低层级导航控件可以保持中性色，不与主要流程操作竞争；
- 不使用渐变球、光斑、装饰插图或无功能图形；
- 图标只用于帮助识别操作或区域，不重复表达已有文字；
- 阴影、边框和背景色均应克制；
- 不为每段内容增加卡片容器；
- 不通过高饱和色竞争学生对正文的注意力。

## 七、学生信息层级

学生进入任务后，默认只需要看到：

1. 当前轮次；
2. 阅读材料；
3. 本题具体考查的能力；
4. 题目；
5. 回答输入区；
6. 保存与提交操作；
7. 提交后的学生可读反馈；
8. 下一步流程入口。

学生区不展示：

- Schema 字段名；
- Runtime ID；
- Evidence 类型、来源和置信度；
- Prompt；
- 模型原始输出；
- Debug JSON；
- 内部状态枚举；
- 单次作答推导出的长期能力标签。

开发者调试信息必须放在独立折叠区域，并与学生主体验明确隔离。

## 八、题目前的信息边界

答题前的信息只负责说明：

> 本题具体考查什么能力。

它不负责提前教学生如何组织答案，也不重复题干要求。

能力说明只能描述题目已经公开的任务目标，不能额外指出题干尚未提供的关键线索、分析路径、解题方法或评分点。若能力说明会帮助学生提前发现本应由其独立识别的线索，应降低提示强度或不展示。

推荐表达：

```text
本题考查根据人物动作和细节推断人物心理的能力。
```

不推荐表达：

```text
练习从文本中找到依据，并把自己的判断说明清楚。
```

原因：

- “找到依据”无法说明摘抄是否有效；
- “说明清楚”缺少可理解的判断边界；
- 容易与题目要求、评分标准和后续反馈混淆；
- 会在真实能力观察前提供笼统答题提示。

## 九、作答引导原则

简单开放题默认不额外展示笼统的作答要求清单。

如果题干已经明确要求学生完成判断并说明理由，页面应直接进入回答区域。

答题前不展示：

- 暗示答案结构的通用步骤；
- 与题干重复的作答要求；
- 抽象的“找依据、说清楚”；
- 评分点的直接改写；
- 可能影响真实诊断的提示。

只有以下情况可以额外展示作答要求：

- 题目明确规定字数；
- 题目明确规定格式；
- 必须完成多个独立子任务；
- 操作方式无法从题干理解；
- 考试规则要求必须显式呈现。

答案输入框使用中性占位文案：

```text
请在这里输入你的回答。
```

PC / 平板键盘输入默认使用边界明确的标准文本框，不使用仅靠横线模拟的纸面输入区。阅读开放题的输入框：

- 初始高度约为 `240px`，避免短答案页面显得过重；
- 随输入内容自动增长；
- 最大高度约为 `400px`，超过后在输入框内部滚动；
- 不开放手动拖拽改变尺寸，避免破坏工作区布局；
- 保留浅灰背景、浅灰边框和蓝色聚焦状态；
- 真正的手写、默写或作文纸任务应使用独立手写画布，不通过普通文本框横线背景模拟。

具体问题分析、缺失内容和改进建议应由提交后的反馈承担。

学生端是否展示作答要求，不影响 Runtime 中正式任务数据的完整性：

- `answerRequirements` 必须继续存在；
- `assessmentBasis` 必须继续存在；
- Rubric 必须继续满足既有 Schema 与诊断要求；
- 展示层可以隐藏当前任务不需要呈现的引导；
- 展示层不得因此删除、改写或弱化正式评价依据。

基本关系是：

```text
Runtime 需要完整
学生端不一定全部展示
```

## 十、题目内容质量原则

界面简洁不能掩盖题目本身的信息缺陷。

阅读材料必须包含足以支撑题目判断的文本线索。题目要求学生推断人物心理时，材料至少应提供可观察的动作、语言、情境或关联信息。

例如，若参考答案涉及父亲对孩子过往的怀念，材料中必须存在父亲与孩子之间的关联线索。不能只依赖参考答案补充材料中不存在的信息。

题干应：

- 指向明确的文本对象；
- 使用学生可以理解的语言；
- 明确要求完成什么判断；
- 避免把评分术语直接交给学生；
- 与材料提供的信息范围一致。

## 十一、交互原则

交互应短、稳、可预期。

要求：

- 空答案不得进入正式提交 Runtime；
- 空答案的提交按钮可以保持可点击，但点击后必须在进入 Runtime 前阻断，并给出操作提示；
- 保存草稿与正式提交必须明确区分；
- 草稿只在学生主动点击“保存草稿”时写入；输入框失焦不得自动触发保存或成功提示；
- 空内容不得写入草稿记录，也不得显示“草稿已保存”；
- 提交过程中防止重复点击；
- 无效答案应原地返回修改，不生成能力结论；
- 分析中应展示明确状态；
- 当前回合正式完成，并且正式结果持久化成功后，才能进入下一轮；
- 草稿保存成功只表示可以恢复当前作答，不代表本轮已经完成；
- 恢复后应继续同一 `learningRoundId`，不能重复启动回合；
- 返回操作必须回到同一 PC 学习流程，不跳转到旧移动端 Demo；
- 页面异常时提供明确、单一的重试入口；
- 不同时展示多个含义相近的反馈卡和操作入口。

### 1. 反馈语言原则

学生反馈必须具体、可核对，并以本次真实作答和正式诊断结果为依据。

反馈内容按来源分为三类：

1. 学生答案中可以逐字定位的内容，可以使用“你写出了……”并引用学生原文；
2. Diagnosis 已明确确认、但经过归纳或同义转换的表现，只能使用“你的回答表达了……”或“你的回答体现了……”；
3. 仍需进一步确认的系统推断，不能作为学生已经完成的事实展示。

引号只用于学生答案中能够逐字找到的原始片段。系统不得把“舍不得”归一化为“不舍”后，再用“你写出了‘不舍’”呈现；也不得为了丰富表达，自动扩写为学生没有写出的多个心理词。

“思路点评”应先把本题正式任务要求拆成可核验的回答环节，再逐项说明完成情况。阅读开放题常见环节包括：

- 是否回答了题目的核心问题；
- 是否使用了题目要求的文本细节；
- 是否说明了文本细节与结论之间的关系；
- 是否完成题目明确要求的其他表达任务。

每个环节只能标记为“已明确完成、部分体现、尚未体现、当前信息不足以判断”之一。内部反馈对象保留全部覆盖状态和来源；学生端只展示最多一至两个已经完成的关键点，以及当前最重要的一个缺口。无法证明某个环节独立成立时，默认不得算作已完成。

覆盖检查不是参考答案关键词匹配。合理异表述只要与材料事实、Rubric 和正式 Diagnosis / Evidence 相容，就可以认定为完成；参考答案不得被当作唯一措辞或唯一推理路径。

文本依据必须是能够独立理解的动作、语句、状态或事实片段。`自己、当时、这样、人物、动作` 等孤立代词、泛词或无谓语片段不得因为字符串重合而进入“回答到位”。正式 Diagnosis 可以在内部确认任务要求已满足，但学生端只有在学生答案中能够定位到完整、有意义的事实片段时，才能具体展示“你注意到了文中的……”。题干已经公开且学生实际使用的动作可以展示；学生尚未发现的材料细节默认只保留在内部覆盖依据中，不直接作为答案线索投喂。

推荐表达：

```text
你写出了父亲感到“怀念、不舍”，并结合“站了很久”和“小心地夹回原处”说明了理由。
```

不推荐表达：

```text
你能够结合文本行为说明人物心理。
```

原因：后者没有指出学生具体做对了什么，学生难以理解，也无法据此稳定复现正确做法。

反馈不得为了显得完整而使用“你认真思考了”“你的推理很好”等无证据评价。没有可靠正向信息时，允许不展示“思路点评”。

“已经完成的思考”回答学生本次完成了什么、为什么这一步有价值；“思考缺口”说明答案连接断在哪里以及造成什么影响；“下一步训练”提供能够补上该连接的思考问题或支架。三者必须由同一组 Task Requirement Coverage、StudentResponse 与唯一主要 Gap 生成，不得由不同模块分别猜测。不得展示 `inference` 等能力码，也不得把“任务基本满足要求、可形成正向能力证据”等内部运行摘要包装成学生优点。若正式 Positive / Growth Evidence 已成立但描述不可直接展示，可以同时绑定学生原答案的精确片段，说明学生本次表达了什么理解；不得因此补造学生未写出的依据或结论。

正式反馈必须经过 `Feedback Action Plan` 将专家判断转换为学生能够直接执行的答案动作：

- “已经完成的思考”引用学生本次实际写出的观点、信息、解释或依据，并说明该动作为什么有助于完成题目；
- “思考缺口”指出答案连接中断的位置和造成的影响，不得只写“答案不完整、缺少细节、需要深入分析”；
- “下一步训练”首次只提供可以立刻执行的思考问题；学生仍无法表达且提示层级明确升级后，才允许给出不包含完整答案的句式支架；
- 当正式任务已有可引用的材料线索时，反馈不得继续使用“人物的具体动作、你的理解、说明关系”等无指向占位表达；
- 提示深度由当前反馈状态控制，默认只提供材料位置或释义提示，不直接复制参考答案。

推荐结构：

```text
已经完成的思考
你写出了“父亲珍惜这片树叶”这一想法。这一步已经开始回应题目要求说明人物心理。

思考缺口
答案直接写出了这个结论，却没有呈现人物做了什么，因此读者看不出判断来自材料中的哪一处。

下一步训练
先别急着改答案。看看材料中的“捏着树叶站了很久”，想一想：这个动作说明父亲当时在想什么？再根据这个心理重新组织答案。
```

当正式原因码为 `conclusion_inconsistent` 时，反馈必须同时比较学生原判断与正式材料线索，并解释两者为何没有对应。不得只显示“结论与材料意思不一致 / 重新查看 / 重新写出”；也不得为了具体而直接泄露标准结论。

反馈区块允许按证据不对称展示：完整回答可以只显示“已经完成的思考”，不强行给出训练建议；全部关键要求都无法判断时不显示完成项，但“思考缺口”可以列明形成最低有效分析所缺少的回答要素。此时不得只写“信息不足”或“暂时无法判断”，应根据正式任务指出需要补充的是核心结论、具体文本依据、依据与结论的解释关系，或其中的组合；不得借此宣布能力缺陷，也不得泄露参考答案。具体属于结论调整、依据缺失还是关系缺失，由正文和结构化原因码表达。

“需要留意”只有在正式诊断提供可靠依据时才展示，并且必须描述本次答案中可以重新检查的具体内容，不得直接给学生贴长期能力标签。

“思路建议”只负责给出学生可以执行的下一步。不得只写“补充具体细节”“用细节支持判断”或“说明清楚”；必须根据题目上下文说明：

- 当前需要的是动作、语言、神态、关键语句还是其他内容；
- 什么样的信息算该类具体内容；
- 学生应怎样把该内容与题目要求联系起来。

例如人物心理题推荐表达：

```text
从文中找出父亲的一个具体动作，写清父亲做了什么或怎样做。
再说明你为什么能从这个动作看出父亲有这样的心理。
```

阅读开放题优先使用“想一想、看出、说明为什么”等直接动作语言。只有题目本身要求作出判断时，才保留“判断”。理解偏差应转成与当前任务目标对应的自然问题，例如“人物当时可能有怎样的心理”或“这些动作表现了人物怎样的特点”，不得使用“理解还需要再检查”等评审式搭配。“问题定位、核心事实冲突、证据不足、能力不足”等内部诊断语言不得进入学生反馈。

### 2. 轮次过渡与间距原则

完成一轮后的页面只承担两项任务：让学生看懂本次反馈，并进入下一轮任务。它不是额外的保存确认页或流程验收页。

要求：

- 只保留一份主要反馈；
- 保存成功仅作为进入下一轮的前置状态，不重复展示多张确认卡；
- 下一步只保留一个主要入口，按钮文案使用明确动作，例如“进入下一轮任务”；
- 主要按钮居中展示，不与反馈正文争夺阅读顺序；
- 反馈标题、反馈内容和下一步按钮之间保持稳定留白；
- 当前反馈容器与下一轮按钮之间使用约 `32px` 间距；
- 间距服务于段落分组和阅读停顿，不使用分割线或装饰卡片代替空间层级；
- 不为了制造“完成感”增加重复标题、重复总结或无功能视觉元素。

### 3. 操作反馈与 Toast 原则

保存、提交和输入校验使用轻量 Toast，不使用阻断式弹窗，也不通过新增页面卡片表达短暂操作状态。

视觉规范：

- Toast 固定在屏幕底部中央；
- 容器使用白色背景、无边框和淡投影；
- 图标使用 `16 × 16px` 线性图标；
- 成功状态使用绿色图标，错误状态使用红色图标；
- 文案使用黑色 `14px / 400`；
- 出现时使用约 `180ms` 的淡入上移动效，消失时使用约 `180ms` 的淡出下移动效；
- 系统开启“减少动态效果”时，应缩短或取消明显位移动效。

时长规范：

| 状态 | 示例 | 默认时长 |
| --- | --- | --- |
| 成功提示 | 草稿已保存 | 约 `2s` |
| 操作提示 | 当前没有可保存的内容、请先输入回答再提交 | 约 `3s` |
| 系统错误 | 草稿保存失败、本轮提交失败、下一轮启动失败 | 约 `6s` |

系统错误与操作提示均可以提供关闭入口。学生继续输入时，与当前输入有关的旧操作提示应立即清除。

异步状态必须遵守“最新操作优先”：

- 点击提交后，仍在执行的旧草稿保存反馈应作废；
- 学生继续输入、进入下一轮或重置流程后，旧保存请求不得回写页面状态；
- 错误 Toast 消失后，不得补发已经过期的“草稿已保存”提示；
- 过期异步结果不得覆盖学生更新后的答案。

### 4. 反馈页与完成页容器规范

轮次反馈页与三轮完成页使用同一套过渡页面规范：

- 页面主区域使用 `#f7f9fc` 浅灰背景，顶栏保持白色；
- 核心信息使用最大宽度 `720px` 的白底容器；
- 容器使用小圆角、无边框和淡投影；
- 反馈容器上下内边距统一使用约 `28px`，首个反馈区块不得再叠加顶部外边距；
- 容器在窄屏下允许自适应收缩，不产生横向滚动；
- 主操作按钮位于容器下方，并与容器保持同一水平中心线；
- 容器与按钮之间使用约 `32px` 间距；
- 反馈页只展示一份反馈和一个“进入下一轮任务”入口；
- 完成页只展示完成图标、必要说明和一个“重新开始”入口；
- 完成页不得重复展示本轮反馈、已做到、继续关注和下一步等已经出现过的信息。

反馈状态标记保持克制且语义统一：

- “回答到位”使用绿色线性勾号，不使用数字编号；
- “思考缺口”使用黄色实心圆点，不使用红色错误符号；
- 标记尺寸应小于正文，并与对应条目的首行文字对齐；
- 颜色只辅助区分状态，标题和正文仍需独立表达完整含义。

### 5. 反馈引导式渐进呈现

首次获得包含“思路点评”和“思路建议”的正式反馈时，页面可以按阅读顺序进行短时区块级渐进呈现：

```text
思路点评标题
→ 点评内容
→ 思路建议
→ 流程操作
```

该效果用于引导阅读，不是模拟模型逐字生成，也不能改变正式学习状态。

要求：

- “思路点评”标题立即出现；
- 点评内容使用约 `180–200ms` 的轻微淡入；
- “思路建议”在约 `500ms` 时出现；
- 流程操作在约 `1s` 时完整出现；
- 总等待时间控制在约 `1–1.2s`，不使用长时间逐字动画；
- 学生点击反馈区域，或按 `Enter / Space`，应立即显示全部内容和操作；
- 学生正在选择文字时，不应意外触发展开；
- 操作区应预留稳定高度，避免按钮出现时页面跳动；
- 单区块简短反馈直接完整显示；
- 阻断、Provider 异常、重试、返回和结束学习等关键状态立即显示，不播放渐进动画；
- 系统启用“减少动态效果”时直接完整显示；
- 同一 `learningRoundId` 的正式反馈首次完整展示后，记录 `feedbackPresentationState = presented`；
- 刷新、返回或恢复已查看反馈时直接完整展示，不重复播放；
- 展示状态只属于本地 UI，不得进入或改变 Feedback、Round、Diagnosis、Evidence、Evaluation 与 Profile。

### 2026-07-23 学生反馈与作答边界校准

本轮继续收紧了“什么内容可以进入诊断”和“正式反馈怎样转化为学生行动”两条边界：

- 开放题只复制全文、材料片段或粘贴与题目无关的完整文本时，不进入具体能力诊断，不形成 Evidence、Profile 更新或内容性反馈；
- 有效但错误的作答仍可进入 Diagnosis；作答有效、答案正确和学习回合完成是三个不同状态；
- 学生反馈统一为“已经完成的思考 / 思考缺口 / 下一步训练”，分别回答已经走到哪里、连接断在哪里、下一步练什么；
- “已经完成的思考”必须引用学生真实完成的行为，并说明其对完成题目的价值，不使用无依据表扬；
- “思考缺口”必须指出具体答案连接及其影响，不停留在“缺少依据、分析不够”等空泛判断；
- “下一步训练”优先给出能够触发思考的检查问题，不默认提供可机械套用的固定句式；
- 反馈图标放在区块标题，正文统一从标题文字起始线对齐；
- 本轮反馈已经完整呈现时，不再追加“下一任务待准备 / 待检查”等低信息量尾声模块，只保留单一返回入口；
- 反馈容器使用浅灰页面、白底淡投影和约 60px 上下留白，操作按钮与容器保持独立停顿空间；
- 上述展示调整只影响学生端表达和页面层级，不改变正式 Diagnosis、Evidence、Evaluation、Profile 或下一任务决策。

### 2026-07-26 平台布局与按钮规范统一

本轮将素材录入、题目审核、学习入口和正式作答区的宽度、排列与操作样式收敛为同一套产品规范：

- 学习入口采用 `1360px` 顶栏与 `1200px` 纵向主体，移除独立的 `1120px` 口径；
- 正式作答区继续以 `1400px` 为最大宽度：PC 与笔记本采用 `40% / 60%`，横屏平板采用 `45% / 55%`，小于 `1024px` 后转为纵向排列；
- 反馈页、完成页与阻断页继续使用约 `720px` 的纵向单栏，不因全局宽度统一而放大阅读行长；
- 常规主要流程操作统一为深蓝实心按钮，次要操作统一为白底深蓝描边，Hover 与 Focus 采用蓝色反馈；
- AI 操作统一使用紫色，完成或通过状态使用绿色，危险操作使用红色；
- 禁用按钮使用中性浅灰并说明不可用原因，返回、关闭与 Toast 关闭等低层级控件保留中性色；
- 本轮只调整页面几何边界、响应式排列与操作视觉，不改变学习、录入、审核、发布或正式 Runtime 语义。

## 十三、体验验收清单

### 通用表单标识规范

- 存在提交、审核、执行或冻结门槛的表单，必填项必须显式标明；
- 条件必填项必须同时说明触发条件，不得只在提交失败后告知；
- 推荐填写但不阻断流程的字段，不得标记为必填；
- 允许保存未完成草稿时，应明确说明“可暂存”与“通过校验”是两个不同状态；
- 错误提示必须对应具体字段和修正方向，不能只显示技术错误码。

PC / 平板工作台进入后，应满足：

- [ ] 学生能快速找到阅读材料；
- [ ] 学生能理解题目要求；
- [ ] 学生知道本题考查的具体能力；
- [ ] 页面没有笼统、重复或提前泄露答题结构的提示；
- [ ] 标准文本输入框初始高度适合短答案，并能随内容增长且不超过约 400px；
- [ ] 阅读和作答不需要频繁切换页面；
- [ ] 空答案不得进入正式提交 Runtime；
- [ ] 空答案点击提交后得到操作提示，但不进入 Runtime；
- [ ] “我不知道”等无效非空回答得到明确操作提示，保留原答案且不进入正式 Diagnosis；
- [ ] 空内容点击保存不会写入草稿，也不会显示保存成功；
- [ ] 点击输入框外部不会自动保存或触发 Toast；
- [ ] 草稿、提交、分析和保存状态清楚；
- [ ] 成功、操作提示和系统错误按 `2s / 3s / 6s` 分级展示；
- [ ] 旧保存请求不会在提交提示结束后补发过期 Toast；
- [ ] 提交后反馈具体且可行动；
- [ ] 反馈标题统一使用“已经完成的思考 / 思考缺口 / 下一步训练”；具体问题类型由正文和原因码表达；
- [ ] 反馈要求补充细节时，能够说明细节类型、具体程度和使用方式；
- [ ] 阅读开放题不滥用“判断、支持判断”等抽象措辞；
- [ ] 正向反馈能指出学生写出的判断及其使用的文本细节；
- [ ] “已经完成的思考”和“思考缺口”均对应本题正式关键点与可追溯事实；
- [ ] 每个关键回答环节具有“已完成、部分体现、尚未体现、信息不足”之一的明确状态；
- [ ] 学生端最多展示一至两个到位点和一个主要缺口，不把完整评分清单暴露给学生；
- [ ] 关键点来自正式作答要求、评价依据和可核验材料内容，不以参考答案措辞作为唯一标准；
- [ ] 合理异表述能够通过动作、对象和状态关系识别，不要求命中参考答案关键词；
- [ ] “自己、当时、这样、那里”等孤立词、泛词和无谓语片段不会被展示为有效文本依据；
- [ ] 具体依据点评能够在学生答案中定位到完整、有意义的事实片段；
- [ ] 只写结论而没有具体事实时，不会被判定为已经使用文本依据；
- [ ] 引用事实但没有解释关系时，文本依据与推理关系分别记录，不把整题误判为完整完成；
- [ ] Positive / Growth Evidence 的内部 `detail`、`observation` 和分析句不会直接或机械改写后进入“回答到位”；
- [ ] 学生端不会出现“回答答案、还答案、答案包含核心结论、答案隐含依据、对应材料中、结论与依据的关系成立”等内部拼接表达；
- [ ] Rubric、Diagnosis 或 Evidence 单独声明完成时，若学生答案中没有可核验依据，不会向学生显示文本依据或推理关系已完成；
- [ ] 学生尚未使用的关键材料细节只用于内部核验，不会通过“思考缺口”直接泄露；
- [ ] “思路点评”说明本次完成情况，“思路建议”说明下一次如何补充，二者不重复；
- [ ] 点评与建议来自同一个 `primaryGapRequirementId`，不会出现点评要求重判结论、建议却默认原结论成立；
- [ ] 回答完整时不强造建议，信息不足时不强造完成度点评；
- [ ] 无法可靠确认覆盖或遗漏时，不强行生成该项点评；
- [ ] 使用“你写出了……”和引号时，内容能够在学生原答案中逐字定位；
- [ ] 同义归纳和系统确认结果使用“表达了 / 体现了”，不伪装成学生原话；
- [ ] 没有可靠诊断依据时，不强行生成正向或不足评价；
- [ ] 下一轮入口单一、明确；
- [ ] 反馈与下一轮入口之间留白清楚，按钮不会紧贴正文；
- [ ] 反馈页和完成页使用一致的浅灰背景、白底容器、淡投影和居中按钮；
- [ ] 反馈容器首个内容区块不会叠加额外顶部间距，上下留白约 60px 且一致；
- [ ] “已经完成的思考 / 思考缺口 / 下一步训练”分别使用标题级绿色点赞、黄色灯泡和黑色铅笔图标；
- [ ] 反馈正文不重复显示区块图标，并与标题文字起始线对齐；
- [ ] “已经完成的思考”只呈现有学生作答证据支撑的思考动作，不显示泛化表扬；
- [ ] “下一步训练”必须绑定当前唯一主要 Gap，并给出可执行的思考问题或支架；
- [ ] 首次正式反馈不得默认展示固定句式；只有存在明确的提示升级状态时才允许展示句式支架；
- [ ] 首次多区块反馈按“已经完成的思考 → 思考缺口 → 下一步训练 → 流程操作”在约 1–1.2 秒内完成展示；
- [ ] 点击反馈区域或按 Enter / Space 可以立即显示全部内容和按钮；
- [ ] 已查看反馈刷新或恢复后不会重新播放渐进动画；
- [ ] 开启“减少动态效果”时反馈直接完整显示；
- [ ] 渐进展示只改变 UI 呈现，不改变正式反馈和学习状态；
- [ ] 阻断、异常和关键恢复操作不会被动画延迟；
- [ ] 已有正式反馈时，不追加“下一任务待准备 / 待检查”等无行动价值的尾声说明；
- [ ] 刷新后能够理解当前处于哪一轮；
- [ ] 学生区不暴露 Runtime 字段；
- [ ] PC 与平板横屏不存在遮挡或文字溢出；
- [ ] 视觉元素不会竞争学生对内容的注意力；
- [ ] 没有必须依赖成人解释才能继续的步骤。

## 十四、当前边界

本次体验校准不证明：

- 已完成正式品牌视觉；
- 已建立完整设计系统；
- 已覆盖所有题型；
- 已完成移动端复杂题体验；
- 已验证长期学习效果；
- 已形成正式商业产品 UI；
- 已完成无障碍与多设备全面测试。

本次校准只证明：

> 已经成立的连续学习闭环，可以用更干净、克制、内容优先的 PC / 平板工作台承载，并且不妨碍学生完成阅读、作答、反馈和连续学习。

## 十五、后续使用方式

后续新增学生学习页面或进入 Phase 13 时，应先检查本文的体验边界。

本文适用于：

- Phase 12 之后的 PC / 平板学生学习主流程；
- 后续延迟复测入口；
- 后续自适应任务呈现；
- 后续 AI Coach 的学生端介入展示；
- 后续复用学习工作台组件的学生页面。

本文不是完整设计系统，也不定义所有产品页面的视觉规范。它是学生学习主流程的体验宪法：

> 高专注、低干扰、信息优先。

若新功能需要增加状态、提示、入口或视觉元素，应回答：

1. 它是否帮助学生理解当前任务？
2. 它是否帮助学生完成当前操作？
3. 它是否属于学生应该看到的信息？
4. 它是否与页面已有信息重复？
5. 删除它是否会影响学生完成学习？

如果删除后不影响学习，应优先不展示。
