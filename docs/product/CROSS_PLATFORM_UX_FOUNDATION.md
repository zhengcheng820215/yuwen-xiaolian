# 跨平台 UX 基础规范

状态：`ACTIVE / SHARED UX FOUNDATION`

文档版本：`v1.1`

生效日期：`2026-08-12`

适用状态：`Accepted`

## 一、目的与适用边界

本文定义 Learning 学生学习平台与资源录入、审核、发布工作台共同遵守的基础体验规则。它只统一品牌、基础组件和无障碍底线，不要求两个平台拥有相同的信息密度、布局或操作颜色。

规范分层如下：

1. 本文：共享基础与跨平台边界；
2. [PC / 平板学习工作台体验校准](./PC_LEARNING_WORKSPACE_UX_CALIBRATION.md)：学生端权威规范；
3. [资源生产工作台 UX 规范](./RESOURCE_PRODUCTION_WORKBENCH_UX_STANDARD.md)：录入、审核、发布端权威规范；
4. [产品颜色语义规范](./PRODUCT_COLOR_SEMANTICS.md)：生产工作台状态色和动作色的权威来源；
5. 工作流与领域契约：决定状态、权限和命令，不由 UX 文档改写。

冲突处理顺序为：领域契约 > 平台专属 UX 规范 > 本文 > 页面局部实现。历史 Demo 和验收报告只保留证据，不覆盖当前正式规范。

## 二、意图驱动的流程原则

### 2.1 总原则

**领域对象数量不等于用户步骤数量。**

领域模型可以为了质量、审计和恢复保留 Material、Plan、Candidate、Revision、Assessment、Human Review、Freeze、Formal Version 与 Registry 等多个对象；前台流程只能根据用户需要完成的判断和决定组织。不得把内部对象的创建、保存或状态迁移逐一翻译成页面、步骤、按钮或确认框。

### 2.2 强制规则

1. **一个用户意图只对应一个主操作。** 同一工作单元在当前时刻只突出一个推进该意图的主按钮；系统可以在按钮后编排多个确定性的领域动作。
2. **没有新增人工判断，就不增加确认步骤。** 重复确认同一个选择、自动检查结果或系统即将执行的确定性写入，不构成新的用户任务。
3. **技术落盘不能伪装成业务里程碑。** 自动保存、创建 Revision、写入 Assessment、冻结版本和登记 Registry 是系统责任；除非用户需要据此做出决定，否则不得占据正常路径的步骤位。
4. **检查是系统能力，决策才是用户任务。** 系统应自动运行可确定的结构检查、语义评估和发布预检，并向用户呈现结论与证据；用户只处理需要人工取舍的阻断、提醒和正式决定。
5. **底层多版本必须可追溯，前台只呈现一个当前工作对象。** 历史版本按需展开；正常编辑、恢复和操作始终指向唯一、明确的当前对象。
6. **失败恢复应恢复工作，不应让用户管理事务状态。** 系统记录已完成阶段并从中恢复，页面提供与用户目标一致的唯一恢复动作，不要求用户理解或手动重放内部事务。
7. **单人模式不模拟不存在的多人审批组织。** 单人生产可在同一工作台连续完成编辑、判断和发布；只有真实存在职责分离、权限边界或独立责任人时，才引入提交、审核和批准等分角色步骤。

### 2.3 设计判定

新增页面、步骤、按钮或确认前，必须依次回答：

1. 用户此刻新增了什么意图或不可替代的人工判断？
2. 如果不增加该步骤，会丢失什么决定、责任或高风险知情确认？
3. 该动作是否只是技术写入、自动检查或内部状态迁移？
4. 系统能否在同一次主操作中确定性完成并保留审计记录？

第 1、2 项没有明确答案，或第 3、4 项答案均为“是”时，不得新增用户步骤。

## 三、两个平台不得机械统一

| 维度 | Learning 学生平台 | 资源生产工作台 |
| --- | --- | --- |
| 用户 | 学生 | 内容生产者、审核者 |
| 首要目标 | 专注阅读、作答、理解反馈 | 高效生产、判断状态、准确追溯 |
| 信息密度 | 低 | 中高 |
| 专业字段 | 默认隐藏 | 按工作需要显示 |
| 页面结构 | 单一学习主线 | 多对象、多状态工作台 |
| 主操作 | 当前唯一下一步 | 当前工作单元唯一主操作，可并列必要工具动作 |
| 颜色 | 绿色可作为学习推进品牌动作 | 严格按动作、AI身份和结果状态区分 |

Learning 学生平台的品牌图标、可操作状态、说明强调条、链接、Toast 信息图标、输入焦点和学习推进按钮统一使用绿色家族，不保留蓝色交互语义。生产工作台仍按其专属颜色规范使用蓝色，二者不得相互覆盖。

禁止为了视觉一致，把生产端的 Revision、Assessment、Registry、内部能力标签带入学生端；也禁止为了“简洁”，从生产端隐藏做出审核和发布决定所需的来源、版本和问题信息。

## 四、共享基础 Token

### 4.1 字体与文本

- 使用系统无衬线字体栈；中文正文不得使用装饰字体。
- 基础正文 `16px`，辅助文字与按钮 `14px`，区块标题 `18px`。
- 长文本行高不低于 `1.7`；辅助文字行高不低于 `1.5`。
- 正文颜色使用深灰，不以纯黑大面积铺陈；辅助文字必须保持可读对比度。
- 不依靠字号之外的颜色单独表达层级。

### 4.2 间距

共享间距基数为 `4px`，常用值为 `8 / 12 / 16 / 24 / 32 / 40px`。

- `8px`：图标与文字、紧密字段关系；
- `16px`：同一工作单元内部；
- `24px`：相邻信息组；
- `32px`：主要区块；
- `40px`：桌面端大区块或页面边距。

页面不得用连续分割线代替间距层级，也不得随意引入 `10 / 18 / 22 / 30px` 等平行节奏。

### 4.3 几何与表面

- 表单、按钮和普通容器优先使用 `6px` 左右的小圆角。
- 边框采用浅灰 `1px`；不通过加粗边框制造焦点，避免布局跳动。
- 阴影只用于浮层、Toast 或确有层级悬浮关系的容器。
- 正文区不连续嵌套卡片；背景、留白和标题应优先承担分组。

### 4.4 控件

- 可点击目标最低高度 `40px`，主要操作建议 `44px`。
- 所有输入控件必须有可见标签或可访问名称。
- 焦点必须清晰可见；键盘操作顺序与视觉阅读顺序一致。
- 禁用状态必须有真实 `disabled` 或 `aria-disabled`，并说明原因。
- 只读、禁用、加载失败和尚未开始必须使用不同文案与组件状态。

## 五、共享状态与反馈底线

- 任何状态都不能只靠颜色表达，必须同时有文字。
- 成功、提醒、阻断和失败的语义不能互换。
- 加载状态说明正在发生什么；超过合理时间后提供恢复或返回入口。
- 保存、提交、发布等异步操作必须防止重复触发和旧结果回写。
- 短暂结果使用 Toast；需要用户处理的问题留在对应工作对象附近。
- 删除、停用、覆盖等高风险动作必须明确对象、影响和可恢复性。

## 六、响应式与滚动基础

- 页面不得产生非必要的横向滚动。
- 响应式变化只改变排列、宽度和必要密度，不改变业务状态和操作含义。
- 驻顶元素必须保留明确层级和不透明背景，不遮挡焦点目标。
- 独立滚动区必须有确定高度、可见边界和合理的滚动接管；不得形成难以退出的嵌套滚动。
- 移动端不得照搬桌面双栏或高密度侧栏，应恢复自然文档流。

## 七、组件归属

### 共享组件

字体、基础输入框、焦点环、禁用态、Toast、错误提示、返回图标、加载指示、无障碍标签可以共享。

### 平台专属组件

- Learning：学习入口、阅读材料、答题区、轮次反馈、下一步动作；
- 生产端：素材选择器、任务卡、AI 候选、质量问题、版本追溯、发布状态、批次摘要。

平台专属组件不得仅因外观相似而强行复用；只有语义、状态和交互合同一致时才能抽为共享组件。

## 八、跨平台变更流程

1. 先判定变更属于共享基础还是某一平台；
2. 核对对应权威 UX 文档和领域契约；
3. 修改正式页面，不以 Demo 代替；
4. 完成桌面、平板和窄屏检查；
5. 检查键盘、焦点、禁用、加载、失败和恢复状态；
6. 若产生新规则，先更新权威文档，再在页面局部实现中引用。

## 九、验收清单

- [ ] 页面明确属于 Learning 或资源生产平台；
- [ ] 未把另一平台的信息密度和专业字段机械复制过来；
- [ ] 字体、间距、圆角、控件高度与共享 Token 一致；
- [ ] 状态不只依赖颜色；
- [ ] 键盘焦点、标签和禁用原因可理解；
- [ ] 桌面无意外页面滚动或横向溢出；
- [ ] 平板和窄屏没有被桌面布局锁死；
- [ ] 异步操作不会重复提交或回写过期结果；
- [ ] 页面局部规则没有覆盖领域状态和权限边界。
- [ ] 页面步骤来自用户意图或新增人工判断，而不是内部领域对象数量；
- [ ] 正常路径没有把自动检查、技术落盘或系统事务暴露成用户里程碑；
- [ ] 前台只有一个当前工作对象，恢复动作不要求用户管理内部事务；
- [ ] 单人模式没有模拟不存在的提交、审核和批准角色。
