## 一、用途与权威边界

本文冻结 Phase 17 题目检查、人工发布决定与正式发布的领域工作流、信息层级、操作语义和质量问题分级。单人生产模式由统一资源生产工作台承载，不再要求独立题目审核平台作为主入口。

现行语义优先级：当前单人模式以 [AI 资源生成与优化工作流契约](./AI_RESOURCE_GENERATION_AND_OPTIMIZATION_WORKFLOW_CONTRACT.md) 的“采用并发布”为唯一用户主决定。本文件中的“保存草稿、重新检查、提交最终确认、发布任务”等页面描述仅适用于历史编辑流程、多人审核模式或失败恢复场景，不得重新组合成当前单人模式的连续步骤。

面向用户的单人 Candidate 主链收口为：

```text
生成题目
→ 人工点击“采用并发布”
→ 系统自动检查、记录确认并发布
→ 正式发布或进入可恢复异常
```

“采用并发布”是单人模式正常路径中的明确人工决定，不是一次不可追溯的领域写入。系统内部仍依次保留创建 Revision、Validation / Assessment、记录 Human Review Decision、Freeze、Formal Version 与 Registry 写入，并持久化每一阶段结果。采用前已经展示的非阻断提醒随该决定按 warning code 分别留痕；阻断问题、采用后新增未确认提醒或任一领域阶段失败时停止并提供阶段恢复动作。多人模式仍可恢复独立提交、审核和发布动作。

平台不要求用户一次性理解所有 Schema、来源、版本和内部质量字段，也不承担训练任务规划或 Material Observation Plan 的重新设计。

本文不替代：

1. [Phase 17 录入字段契约](./AUTHORING_FIELD_CONTRACT.md)；
2. [Phase 17 录入、审核与发布职责边界契约](./AUTHORING_REVIEW_PUBLICATION_RESPONSIBILITY_CONTRACT.md)；
3. [Phase 17 单训练任务重新生成契约](./SINGLE_TRAINING_TASK_REGENERATION_CONTRACT.md)；
4. [Phase 17 训练任务组 AI 规划契约](./TRAINING_TASK_GROUP_AI_PLANNING_CONTRACT.md)；
5. Question Draft、Revision、Validation、QuestionQualityAssessment、Human Review、Freeze 与 Formal Resource 的既有数据和运行规则。

本文只负责把上述业务契约翻译为稳定、清晰、低负担的审核工作流。字段、保存、检查、审核、发布和问题定位不得在页面中形成第二套解释。

本文描述的是完整平台工作流，不要求同一用户完成所有阶段。内容编辑者、审核者和发布者可以是同一用户，也可以由后续权限模型分离；无论角色如何分配，各阶段的数据、Revision 和状态边界不得改变。

内容编辑、人工裁决与正式化的职责划分以“录入、审核与发布职责边界契约”为准。职责边界不再等同于页面边界：在单人模式中，编辑、内联质量处理和人工发布决定可以在同一任务卡连续完成；多人模式才可恢复独立只读审核入口。

## 二、平台主任务与非目标

### 2.1 用户进入平台需要完成什么

用户在统一工作台中只需要依次回答五个问题：

1. 当前正在处理哪一道题；
2. 题目、学生任务和评分规则是否正确；
3. 系统发现了哪些必须处理或需要关注的问题；
4. 当前内容是否已经保存并基于最新 Revision 完成检查；
5. 当前题目是否可以发布；若不能，下一步具体修改什么。

### 2.2 平台不负责什么

题目审核与发布平台不负责：

1. 从零规划整组训练任务；
2. 重新选择 Material Observation Plan 的能力覆盖方向；
3. 在预览页面编辑正式内容；
4. 通过页面展示推断或拼装另一套正式状态；
5. 使用系统检查结果替代人工审核决定；
6. 在点击发布后才首次暴露已知阻断问题。

若问题来源于 Plan 管理的受控字段，平台应准确说明冲突，并定位到统一工作台中的对应任务卡或执行已有受控同步能力，不得诱导用户反复改写无关题干。

## 三、信息层级

页面信息固定为四层：

| 层级 | 用户问题 | 内容 | 默认状态 |
| --- | --- | --- | --- |
| 一级 | 我现在处于什么状态，下一步做什么 | 当前题目、当前状态、未保存状态、检查时效、下一步动作、发布准备状态 | 始终显示 |
| 二级 | 这道题到底要求学生做什么 | 题目、学生任务、观察目标、能力目标、具体训练点、材料范围 | 默认展开 |
| 三级 | 系统如何判定回答是否满足要求 | 评分项、答案接受范围、最低作答要求、参考答案或答案示例 | 默认展开；长内容可在模块内折叠 |
| 四级 | 这道题从哪里来，如何追溯 | 高级设置、来源说明、版权说明、内部版本、规则版本、历史 Revision | 默认折叠 |

### 3.1 当前状态与下一步

一级信息必须同时表达：

1. 当前生命周期状态；
2. 是否存在未保存修改；
3. 当前 Assessment 是否仍然有效；
4. 是否存在阻断问题；
5. 唯一推荐的下一步动作。

禁止只显示“草稿”“检查通过”或“发布未完成”等孤立状态，让用户自行推断下一步。

推荐表达：

```text
当前状态：内容已修改，等待保存并重新检查
下一步：保存当前修改并重新检查题目
```

### 3.2 质量问题区

存在未解决问题时，质量问题区自动展开，并按严重程度排序：

```text
阻断问题
→ 人工关注
→ 优化建议
```

全部问题已解决时，质量问题区收起为摘要：

```text
系统检查通过
7 项通过，0 项阻断，0 项人工关注
```

系统检查通过不等于人工审核通过，也不等于已经发布。

### 3.3 训练任务列表

统一工作台的训练任务列表承担当前批次导航；题目正文外显，详细字段在任务卡内展开编辑：

1. 使用稳定题号，不因筛选状态重新编号；
2. 展示题目摘要、生命周期状态和未处理问题数量；
3. 选中题目使用明确选中样式；
4. 点击后切换主编辑区；
5. 不在列表内复制完整评分、检查和发布操作。

题目内容应完整可读，空间不足时可以通过展开或主编辑区查看，不得以不可交互的省略号隐藏关键内容。

## 四、单页工作区职责

本节所称编辑区、预览区、质量问题区和发布操作区均属于统一资源生产工作台的内联区域，不代表独立审核页面。

| 页面区域 | 唯一职责 | 禁止行为 |
| --- | --- | --- |
| 批次题目列表 | 题目导航、状态扫描、问题数量扫描 | 不直接编辑，不触发发布 |
| 主编辑区 | 修改当前题目的正式内容 | 不展示历史检查为当前结论 |
| 质量检查区 | 解释问题、定位字段、显示解决状态 | 不替代人工审核 |
| 任务卡操作区 | 正常路径显示`采用并发布`，异常时显示唯一恢复动作 | 不混入无关字段编辑，不暴露并列审核步骤 |
| 学生预览 | 验证学生实际看到的题目与材料 | 不提供编辑 |
| 审核预览 | 验证审核者将要确认的内容与依据 | 不产生隐式修改 |
| 来源与追溯区 | 查看来源、Revision、规则版本和历史记录 | 不占用首层主要空间 |

### 4.1 编辑与预览边界

预览页始终只读。需要修改时必须返回主编辑区，并保持当前题目、问题和字段定位上下文。

从预览返回不得：

1. 跳回批次第一题；
2. 丢失当前 Material、Plan 或 Draft；
3. 新建重复 Draft；
4. 把预览操作误记为内容修改。

## 五、内容与生命周期状态

页面需要区分内容状态和流程状态，不能把它们混成一个标签。

### 5.1 内容状态

```text
clean
→ 当前页面内容与已保存 Draft Revision 一致

dirty
→ 页面存在尚未保存的质量相关修改
```

### 5.2 检查状态

```text
not_checked
→ 当前 Revision 尚无正式检查

current
→ Validation 与 Assessment 均绑定当前 Revision 和当前规则版本

stale
→ 内容或规则已变化，旧检查只能用于历史追溯
```

### 5.3 审核与发布状态

```text
draft
→ pending_review
→ approved
→ frozen
→ published
```

系统检查、人工审核和正式发布是三个不同判断：

```text
Validation / QuestionQualityAssessment
→ 系统检查

Human Review Decision
→ 人工审核

Freeze / Formal Resource Publication
→ 正式发布
```

### 5.4 当前有效 Assessment 的唯一计算

页面、提交审核和发布不得各自拼装 Assessment 是否有效的判断。系统必须提供一个领域层唯一状态解析器，并由所有入口共同消费。

```ts
type CurrentAssessmentState =
  | { kind: 'missing' }
  | { kind: 'current' }
  | { kind: 'stale_by_revision' }
  | { kind: 'stale_by_validation' }
  | { kind: 'stale_by_rule_version' }
  | { kind: 'stale_by_context' }
  | {
      kind: 'failed';
      stage: 'semantic';
      status: 'provider_failed' | 'timeout' | 'invalid_output';
    };
```

判定当前有效至少必须同时满足：

1. `assessment.draftId === draft.draftId`；
2. `assessment.resourceId === draft.resourceId`；
3. `assessment.assessedDraftRevision === draft.revision`；
4. `assessment.validationId === validation.validationId`；
5. `assessment.ruleVersion === currentRuleVersion`；
6. 需要批次比较时，`comparisonContextHash` 与当前比较上下文一致；
7. Validation 绑定当前 Draft Revision 且已经通过；
8. 语义质量检查属于正式流程时，其执行状态为 `completed`。

现有 `isCurrentQuestionQualityAssessment` 与 `requireCurrentQuestionQualityAssessment` 是领域判断基础。工程实现应在此基础上提供可解释的状态解析结果，不得在页面新增另一套布尔判断。

`stale` 是旧 Assessment 相对于当前编辑上下文的计算结果，不是对历史 Assessment 记录的状态改写。旧记录必须保持不可变并继续用于追溯。

### 5.5 审核中的编辑权限

进入 `pending_review` 后：

1. 题目、学生任务、观察目标、评分标准和其他正式内容字段默认只读；
2. 审核意见与审核决定仍可操作；
3. 如需修改正式内容，必须先执行“退回修改”；
4. 返回 `draft` 后才允许编辑并产生新 Revision；
5. 禁止在审核中静默修改内容，否则 Human Review 与页面内容将不再指向同一 Revision。

`approved`、`frozen` 和 `published` 状态下的正式内容同样不可原地修改。`published` 后续调整必须先基于当前 Formal Resource Version 生成新的不可变 Question Candidate；采用后才允许在同一 Lineage 下创建新 Draft Revision。完整边界以 [正式资源不可变性契约](./FORMAL_RESOURCE_IMMUTABILITY_CONTRACT.md) 为准。

`reviewed` / `approved` 状态下如在发布前发现内容问题，必须先撤销当前发布流程并退回修改。修改后创建新 Draft Revision，旧 Human Review Decision 继续绑定原 Revision，仅用于追溯；禁止修改已审核 Revision 后继续沿用原审核结论。

## 六、操作语义

### 6.1 内部领域动作表

下表描述可追溯的内部领域动作，不等于当前页面按钮。当前单人模式正常路径只显示“采用并发布”；保存、重新检查、人工决定和正式发布由应用层编排，只有异常恢复时才显示对应恢复动作。历史“提交人工审核、审核通过、发布任务、发布正式题目”不得重新并列为页面步骤。

| 内部领域动作 | 内容副作用 | Revision 行为 | Assessment 行为 | 生命周期行为 |
| --- | --- | --- | --- | --- |
| 保存草稿 | 保存当前正式字段 | 仅在内容发生变化时创建新的 Draft Revision | 旧 Assessment 保留为历史，但对新 Revision 失效 | 保持 `draft` |
| 重新检查 | 不修改内容 | 不创建 Revision | 基于当前 Revision 和当前规则版本生成或幂等复用 Validation 与 Assessment | 不改变人工审核状态 |
| 保存并重新检查 | 依次执行“保存草稿”和“重新检查” | 有内容变化时最多创建一个新 Revision | 检查新 Revision | 保持 `draft` |
| 提交绑定（历史命令：提交人工审核） | 不修改内容 | 不创建 Revision | 只读取当前有效结果 | 建立当前 Revision 与 Assessment 的待决定绑定 |
| 记录人工决定（历史命令：审核通过） | 不修改内容 | 不创建 Revision | 不替代 Assessment | 为当前 Revision 记录 Human Review Decision |
| 退回修改 | 不修改题目内容 | 不创建 Revision | 当前结论保留追溯；后续修改将使其失效 | `pending_review` → `draft` |
| 拒绝采用 | 不修改题目内容 | 不创建 Revision | 保留追溯 | 为当前 Revision 记录拒绝决定 |
| 冻结并正式化（领域命令：发布正式题目） | 不修改 Draft 内容 | 不创建新的 Draft Revision | 只消费当前有效检查 | 对已形成决定的当前 Revision Freeze，并幂等创建正式版本 |

单人模式前台只提供“采用并发布”。该应用层动作顺序执行或恢复“采用 Candidate、创建 Revision、检查当前 Revision、记录人工决定、发布正式题目”，但每个领域动作仍遵守上表，不得隐式读取最新 Revision 或跳过 Assessment 当前性校验。

### 6.2 保存规则（历史编辑流程 / 多人模式）

保存草稿必须满足：

1. 无内容变化时不创建空 Revision；
2. 重复点击同一内容只产生一个等价保存结果；
3. 保存后的 Revision 必须能够刷新恢复；
4. 旧 Revision、旧 Assessment 和旧 Review 保留用于审计；
5. 新 Revision 不继承旧 Assessment 的“当前有效”身份。

### 6.3 重新检查规则（历史编辑流程 / 异常恢复）

重新检查：

1. 不创建内容 Revision；
2. 只检查已经保存的当前 Revision；
3. 同一 Revision、同一规则版本、同一输入的重复检查幂等复用；
4. 页面存在未保存内容时，不得对旧保存内容执行检查并将结果伪装成当前结论；
5. 可以在界面中提供“保存并重新检查”的组合动作，但底层必须保持两个独立 Command。

### 6.4 内部提交绑定规则

建立当前 Revision 与 Assessment 的提交绑定前置条件：

1. 当前内容已保存；
2. Validation 绑定当前 Revision；
3. QuestionQualityAssessment 绑定当前 Revision 和当前规则版本；
4. 没有未解决阻断问题；
5. 非阻断人工关注已处理或显式接受；
6. 当前 Plan、Material 和 Draft 身份一致。

### 6.5 人工发布决定记录规则

人工审核决定必须绑定：

```ts
type HumanReviewBinding = {
  draftId: string;
  draftRevision: number;
  validationId: string;
  assessmentId: string;
  reviewedBy: string;
  reviewedAt: string;
};
```

系统检查通过不得在没有用户采用决定时自动创建人工审核通过决定。单人模式中，用户点击“采用并发布”即为明确的人工决定输入；系统必须把该决定绑定到用户采用的 Candidate，以及随后确定性创建并检查的 Revision 与 Assessment Bundle，而不是自动批准或隐式读取后台最新版本。

多人模式中，录入人员对非阻断提醒的保留确认与审核人员的接受决定必须分别持久化。单人模式中，同一次“采用并发布”可以驱动两个独立领域记录，但不得增加第二次用户确认；每个 warning code 仍须独立留痕。审核决定至少绑定：

```ts
type ReviewWarningDecision = {
  warningDecisionId: string;
  draftId: string;
  draftRevision: number;
  assessmentId: string;
  warningCode: string;
  decision: 'accepted' | 'rejected';
  reviewedBy: string;
  reviewedAt: string;
};
```

P0 以 `assessmentId + warningCode` 绑定当前 Warning；独立
`warningAcknowledgementId` 在录入端确认理由持久化完成后作为附加追溯关系接入。
所有必须确认事项必须逐项形成决定。存在未决事项时不得审核通过；任一事项被拒绝时，当前提交整体进入 `revision_required`，不得建立部分审核通过状态。

### 6.6 发布规则

发布前必须在任务卡内提前展示发布准备状态。禁止用户点击发布后才首次看到系统已经知道的阻断项。

发布前检查至少包括：

1. 当前内容已保存；
2. 当前结构与质量检查有效；
3. 当前 Revision 已人工审核通过；
4. Plan 管理的受控设置一致；
5. Material、来源、Observation Link 和正式资源身份完整；
6. 当前 Revision 尚未以同一正式身份重复发布。

发布是幂等操作。重复点击不得生成多个 `FrozenQuestionResourceVersion`、Formal Resource Version 或重复 Registry Entry。

### 6.7 发布部分失败与恢复

正式发布可能跨越：

```text
Freeze 当前审核通过的 Revision
→ 写入 FrozenQuestionResourceVersion
→ 更新 ResourceRegistryEntry
→ 写入 FrozenQuestionQualityTrace
→ 写入 ResourceObservationLink
```

正式主链必须先完成 Plan、Task、Material、当前 Assessment 和 Human Review 的一致性检查，再通过应用层发布命令依次持久化 Freeze、Version、Registry、Quality Trace 与 Observation Link。若底层存储无法提供跨阶段事务，必须保存可恢复进度；已经成功的 Human Review、Freeze 或 Formal Version 不得回滚、覆盖或重复创建。

重复执行同一发布命令必须复用同一组正式身份；当四个对象均已存在且内容一致时，Repository 返回幂等成功，不得增加共享存储 Revision。

旧版本曾允许 Observation Link 后置写入。为兼容这类历史部分状态，恢复命令仍可只补齐缺失对象，但不得把兼容恢复路径重新作为新发布的默认实现。对于无法保证跨存储事务的外部适配器，必须记录可恢复进度：

```ts
type PublicationProgress = {
  draftId: string;
  resourceId: string;
  resourceVersionId?: string;
  registryWritten: boolean;
  status:
    | 'not_started'
    | 'formal_version_created'
    | 'completed'
    | 'partially_completed';
  failedStep?: 'formal_version' | 'registry' | 'quality_trace' | 'observation_link';
};
```

恢复规则：

1. 新发布若发生部分成功，必须进入 `publication_incomplete`，不得伪装成“未发布”或“已发布”；
2. 若读取到历史部分状态，重试必须复用原 `resourceVersionId`；
3. 历史恢复只补齐缺失的 Registry、Quality Trace 或 Observation Link，不得再次 Freeze 或提高版本号；
4. 同一 `draftId` 和同一审核通过 Revision 必须得到同一个正式版本；
5. 页面应明确显示“发布未完成，可继续完成发布”，不得把历史部分成功伪装成完全失败；
6. 发布完成前不得让 Runtime 把缺少有效 Registry 或 Observation Link 的版本视为可用正式资源；
7. 历史正式版本不得因重试或补写关联被覆盖；
8. Human Review 已成功但 Publication 失败时，页面显示“已确认，发布未完成”并提供“重试发布”；
9. 发布失败不得把审核状态回滚为待审核，也不得重复创建 Human Review Decision。

### 6.8 单页发布编排

统一工作台不得再展示独立“提交最终确认”模块、版本选择器或跳转到另一生产页面的“进入审核”按钮。

前台主操作固定为：

```text
采用并发布
```

这里的“采用并发布”是单人 Candidate 正常路径的产品文案；下方 `PublishTaskRequest` 仍是应用层发布编排请求名称，不代表页面需要重新出现“发布任务”按钮。

调用至少携带：

```ts
type PublishTaskRequest = {
  draftId: string;
  expectedRevisionId: string;
  assessmentBundleId: string;
};
```

处理规则：

1. `expectedRevisionId` 与当前持久化 Revision 不一致时返回 `QUESTION_DRAFT_REVISION_CONFLICT`；
2. Assessment 不属于该 Revision、规则版本已变化或检查未完成时阻断发布；
3. 黄色提醒可以由用户在任务卡内接受，接受记录绑定当前 Revision 与 Assessment；
4. 红色阻断必须定位修改，不能通过接受绕过；
5. 幂等键使用 `publish:{draftId}:{expectedRevisionId}` 或等价稳定身份；
6. 成功后状态为 `published`；部分成功为 `publication_incomplete` 并提供“重试发布”；
7. 已发布正式版本不可覆盖；后续调整先创建绑定 `baseFormalVersionId` 的新 Candidate，采用后才创建同一 Lineage 下的新 Draft Revision，并发布为新 Formal Resource Version；
8. 新版完整发布前，原活动版本继续供 Runtime 使用。

## 七、质量问题分级

### 7.1 阻断问题

阻断问题必须修复后才能提交审核或发布。

典型情况：

1. 必填正式字段缺失；
2. 题目绑定的能力、任务用途、材料范围等受控字段与当前 Plan 冲突，且无法由适配规则解释或同步；
3. Validation 或 Assessment 已失效；
4. Rubric、Answer Acceptance 或材料来源缺少正式运行所需的最低结构；
5. 当前 Revision 尚未完成要求的人工审核；
6. 发布身份冲突或来源链断裂。

内容措辞与 Plan 观察点存在轻微偏差，不得仅凭文本差异直接升级为阻断。

### 7.2 人工关注

人工关注表示系统发现风险，但不能独立作出最终判断。

典型情况：

1. 题目与同批其他题目可能考查相同内容；
2. 题目、学生任务和观察目标可能职责性重复；
3. 评分项区分度可能不足；
4. 材料依据表达可以更明确；
5. 难度和作答要求可能存在偏差，但尚未形成受控字段冲突。

人工关注允许：

```text
定位修改
或
接受当前设计
```

接受当前设计必须绑定当前 Revision，并记录操作人、时间和理由。内容再次修改后，原接受记录不得自动适用于新 Revision。

### 7.3 优化建议

优化建议不阻止保存、提交审核或发布，用于改善：

1. 文案清晰度；
2. 页面可读性；
3. 非关键表达；
4. 不影响质量判断的可选元数据。

优化建议不得使用阻断色彩或阻断按钮。

## 八、问题对象与统一提示结构

每个质量问题至少使用以下结构：

```ts
type ReviewIssueSeverity =
  | 'blocking'
  | 'attention'
  | 'suggestion';

type ReviewIssueStatus =
  | 'open'
  | 'needs_recheck'
  | 'resolved'
  | 'accepted';

type ReviewIssue = {
  issueId: string;
  draftId: string;
  draftRevision: number;
  assessmentId: string;
  severity: ReviewIssueSeverity;
  fieldKey: AuthoringFieldKey;
  message: string;
  currentValueSummary?: string;
  recommendation?: string;
  status: ReviewIssueStatus;
};
```

页面提示固定展示：

1. 问题字段；
2. 为什么有问题；
3. 当前内容摘要；
4. 建议修改方向；
5. 定位修改；
6. 接受当前设计，仅限非阻断项。

禁止只显示“可能不一致”“缺少依据”或“需要修改”等无法执行的结论。

## 九、问题处理闭环

正式闭环为：

```text
发现问题
→ 定位修改
→ 展开目标模块
→ 聚焦并高亮目标字段
→ 用户修改
→ 标记当前内容未保存
→ 旧 Assessment 失效
→ 保存新 Revision
→ 重新检查
→ 新 Assessment 判断问题是否关闭
```

### 9.1 定位修改

定位修改必须：

1. 切换到问题所属题目；
2. 展开目标模块；
3. 滚动到目标字段；
4. 将输入焦点放入准确控件；
5. 使用短暂高亮帮助确认位置；
6. 不创建 Revision，不修改字段值。

若字段由 Plan 管理，定位动作必须进入对应任务调整入口或执行已定义的受控同步，不得错误定位到题干。

### 9.2 修改后的问题状态

用户修改相关字段后，原问题不得立即显示“已解决”。

正确状态是：

```text
needs_recheck
```

推荐文案：

```text
内容已修改，等待保存并重新检查
```

只有绑定新 Revision 的正式 Assessment 确认问题不再成立时，问题才能进入：

```text
resolved
```

### 9.3 未保存保护（历史编辑流程）

当前题目存在未保存修改时：

1. 切换其他题目必须提供明确三选项：

```text
当前题目有未保存修改

[保存后切换]
[放弃修改并切换]
[取消]
```

2. 进入预览必须明确预览的是当前页面内容还是已保存内容；
3. 提交审核保持不可用；
4. 不能显示旧检查为当前结论；
5. 刷新或返回时不得静默丢失修改。

“保存后切换”只执行保存和导航，不自动重新检查、不提交审核。保存失败时必须停留在当前题目。“放弃修改并切换”必须恢复当前已保存 Revision 后再导航。题目列表切换、浏览器返回、刷新和进入预览应复用同一离开保护规则。

## 十、发布准备前置（领域计算 / 多人模式与异常恢复）

发布准备区必须在发布动作可见前完成计算。

推荐结构：

```text
发布准备
3 / 4 项完成

✓ 当前内容已保存
✓ 结构与质量检查对应当前版本
✓ 已完成人工审核
△ 题目设置与训练计划一致
```

存在未完成项时，页面直接提供：

1. 具体差异；
2. 应修改的对象；
3. 修改位置；
4. 解决动作；
5. 处理后需要重新执行的检查。

禁止把已知问题延迟到“发布正式题目”点击之后。

## 十一、Command 与数据边界

页面操作应映射到独立 Command：

```ts
saveQuestionDraft
runQuestionValidation
runQuestionQualityAssessment
resolveCurrentAssessmentState
submitQuestionForHumanReview
recordHumanReviewDecision
returnQuestionForRevision
freezeAndPublishQuestion
resumeQuestionPublication
locateReviewIssue
acceptReviewAttention
```

允许界面把保存和检查组合为一个按钮，但禁止多个业务动作共享无法辨认副作用的模糊 Handler。

数据写入边界：

```text
字段编辑
→ 仅更新页面编辑缓冲区

保存草稿
→ 有变化时创建新 Draft Revision

重新检查
→ 写入或幂等复用当前 Revision 的 Validation / Assessment

提交审核
→ 改变审核生命周期，不修改内容

人工审核决定
→ 写入绑定当前 Revision 的 Review Decision

发布
→ Freeze 当前已审核 Revision，并创建或复用正式资源版本
```

### 11.1 角色与动作边界

| 角色 | 允许的正式动作 | 不得产生的隐式副作用 |
| --- | --- | --- |
| 内容编辑者 | 编辑、保存、重新检查、提交当前 Revision 进入最终确认 | 不自动形成确认决定或正式发布 |
| 确认者 | 记录确认通过、退回修改、拒绝采用 | 不在 `pending_review` 中静默修改正式内容 |
| 发布者 | 检查发布准备、完成或恢复正式发布 | 不创建新的内容 Revision |

同一用户可以承担多个角色，但每个动作仍必须遵守对应 Command 和数据写入边界。

## 十二、颜色与状态表达

颜色遵循 [产品颜色语义](./PRODUCT_COLOR_SEMANTICS.md)：

| 颜色 | 工作流含义 |
| --- | --- |
| 绿色 | 通过、成功、已完成 |
| 红色 | 失败、阻断、不可继续 |
| 黄色 | 提醒、人工关注、需要注意 |
| 蓝色 | 选中、定位、动作、执行、当前步骤 |
| 紫色 | AI 生成、AI 建议、智能处理 |

颜色不能作为唯一信息来源。状态必须同时具有清晰中文文案。

## 十三、工程验收标准

### 13.1 动作与版本

1. 修改正式字段后页面立即进入未保存状态；
2. 保存有变化的内容只创建一个新 Draft Revision；
3. 无变化重复保存不创建空 Revision；
4. 重新检查不创建内容 Revision；
5. 同一 Revision 的重复检查、提交和发布满足幂等规则；
6. 发布后正式版本不可被后续 Draft 修改覆盖。

### 13.2 Assessment 时效

1. 修改任一质量相关字段后旧 Assessment 立即失效；
2. 旧结果只作为历史记录，不继续显示为当前结论；
3. 保存并重新检查后，新结果绑定新 Revision；
4. 提交审核只消费当前有效结果；
5. 规则版本变化后旧 Assessment 不再作为当前审核依据；
6. 页面、提交审核和发布对同一输入得到相同的 `CurrentAssessmentState`；
7. Validation、比较上下文或语义检查状态变化时能够返回准确的失效或失败原因；
8. 状态解析不得改写历史 Assessment。

### 13.3 问题闭环

1. 阻断、人工关注和优化建议具有不同提交行为；
2. 点击定位修改准确切换题目、展开模块并聚焦字段；
3. 编辑问题字段后状态变为等待重新检查，而不是直接解决；
4. 新 Assessment 通过后问题才关闭；
5. 接受当前设计只适用于非阻断项，并绑定当前 Revision；
6. Plan 受控字段问题不会错误定位到题干。

### 13.4 页面职责

1. 右侧列表只承担批次导航和状态扫描；
2. 主编辑区是唯一正式内容编辑位置；
3. 学生预览和审核预览均为只读；
4. 一级状态始终可见；
5. 高级设置和追溯信息默认折叠；
6. 发布阻断在发布按钮可用前已经显示。

### 13.5 审核中只读与切换保护

1. `pending_review` 下正式内容字段只读；
2. 点击“退回修改”后返回 `draft`，才允许编辑；
3. 未保存时切换题目显示“保存后切换、放弃修改并切换、取消”；
4. 保存失败不得切换；
5. “保存后切换”不自动检查或提交审核；
6. 浏览器返回、刷新和进入预览复用同一保护规则。

### 13.6 历史编辑流程端到端回归

以下链路保留用于历史编辑流程和多人模式回归，不定义当前单人 Candidate 正常路径：

```text
选择题目
→ 定位一个质量问题
→ 修改对应字段
→ 旧 Assessment 失效
→ 保存形成一个新 Revision
→ 重新检查
→ 问题关闭
→ 提交最终确认
→ 记录确认通过决定
→ 发布任务
→ 重复发布不产生重复正式版本
```

同时覆盖：

1. 切换题目时的未保存保护；
2. 从预览返回后保持当前题目和字段上下文；
3. 退回修改后只修订当前题目，不批量生成兄弟 Draft；
4. 发布前 Plan 差异能够前置显示并准确定位；
5. 刷新恢复后当前 Revision、Assessment 和 Review 身份一致。

发布恢复至少覆盖：

```text
创建 FrozenQuestionResourceVersion 成功
→ Registry 写入失败
→ 页面显示发布未完成
→ 重试发布
→ 复用原 resourceVersionId
→ 只补齐 Registry
→ 不产生新的正式版本
```

## 十四、实施顺序

### P0：工作流状态与问题闭环

1. 建立领域层唯一 Assessment 状态解析器；
2. 让页面、提交审核和发布共同消费该解析结果；
3. 冻结 `pending_review` 正式内容只读规则；
4. 统一保存、检查、审核、退回修改和发布的 Command；
5. 落地阻断、人工关注和优化建议；
6. 修复 Assessment 失效与问题关闭条件；
7. 完成题目切换、返回、刷新和预览的未保存保护；
8. 将发布阻断前置到发布准备区；
9. 补齐发布部分失败后的幂等恢复；
10. 保证定位修改准确命中字段。

### P1：信息层级与页面职责

1. 落地四层信息结构；
2. 固定默认展开和折叠规则；
3. 收敛右侧列表、主编辑区、检查区和底部操作区；
4. 统一学生预览、审核预览的只读边界；
5. 完成未保存保护和返回上下文恢复。

### P2：批次效率与可观察性

1. 提供批次问题数量和状态扫描；
2. 记录问题定位、修改、重新检查和关闭耗时；
3. 统计阻断率、人工接受率和重复修改次数；
4. 用真实十篇素材验证问题分级与工作流负担；
5. 不在 P0 / P1 未稳定前继续堆叠新的审核入口。

## 十五、当前结论

题目审核与发布平台不是字段全集浏览器，而是一条受控决策链：

```text
当前题目
→ 当前问题
→ 准确修改
→ 保存当前 Revision
→ 重新检查
→ 人工审核
→ 正式发布
```

页面优化必须优先降低三类风险：

1. 不知道改哪里；
2. 不知道怎么改；
3. 修改后仍沿用旧检查或在发布末端才暴露问题。

本契约冻结工作流和交互语义，不新增教育判断，不降低 Validation、Assessment、Human Review 或 Freeze 标准。


6. 批次指标由领域层汇总器统一计算，页面只消费汇总结果，不重复拼装统计口径。

对应自动化回归覆盖：

- 批次状态和问题数量汇总；
- 阻断率与提醒人工接受率；
- 重复修改次数；
- 审核、发布和问题关闭耗时；
- 旧数据不推断耗时；
- 既有质量进度、录入、Command E2E 和 Phase 17.5B 回归。

对应浏览器验收覆盖：

```text
真实审核批次
→ 展示批次处理概览
→ 历史缺失指标显示“暂无数据”
→ 桌面与 390px 移动端无横向溢出
→ 页面无新增运行时错误
```

截至 2026-07-30，P2 第三项 Observation Link 原子性已经完成工程对齐：

1. 新发布通过同一个共享存储 CAS 事务写入 Frozen Version、Registry、Quality Trace 与 Observation Link；
2. Observation Link 的 Plan、Task、Material 和 Review 一致性问题在写入正式对象前返回；
3. 事务失败不会留下新 Version、Registry、Trace 或 Link；
4. 相同发布命令重试复用同一组对象，不增加共享存储 Revision；
5. 历史部分成功状态继续由独立恢复命令兼容，不再由新发布主链产生。

对应故障注入与回归覆盖：

- 四对象原子写入；
- 写入失败后四类对象均不存在；
- 失败重试只产生一组正式对象；
- 完成后重复重试不增加存储 Revision；
- 既有发布恢复与 Workbench Command E2E 不回退。

P2 后续仅剩真实十素材校准。

## 十七、历史工程对齐与迁移记录

本节及其后的 2026-07-30 工程记录保留旧审核平台形成过程、回归证据和兼容要求。其中“提交最终确认”“进入最终确认”、审核页签、右侧批次栏及独立页面跳转属于历史交互，不再定义当前单人生产主界面。当前交互以第一至十六节，尤其是 6.8 为准；其中 Revision、Assessment、Human Review、Freeze、幂等与失败恢复规则仍继续有效。

### 17.1 唯一门禁

审核页的检查摘要、待确认事项和审核按钮必须消费领域层同一份当前性判断，不允许组件分别推断。

当当前 Revision 的检查记录不完整或已经失效时，页面进入“待重新检查”状态：

```text
录入检查记录不完整
→ 待确认事项只读
→ 不允许接受提醒
→ 不允许审核通过
→ 退回录入端保存并重新检查
```

该状态不是新的业务生命周期，只是当前 `pending_review` 提交缺少有效审核依据时的页面门禁。

### 17.2 待确认事项

完整检查记录下，每个事项仍按以下顺序呈现：

```text
系统提醒
→ 录入人员处理
→ 录入人员说明
→ 审核者决定
```

检查记录不完整时，不展示可操作的“接受该处理”。页面说明原因，并把“退回录入修改”作为恢复路径。禁止审核者先接受提醒，再等待录入端补检查记录。

### 17.3 审核操作与治理操作

审核决策区只承载：

```text
退回录入修改
审核通过
```

提交者主动撤销尚未形成决定的提交属于治理操作，统一命名为“撤回至录入端”，放入“更多操作”。撤回不等于退回，不记录审核拒绝，也不创建内容 Revision。

### 17.4 状态投影

页面必须区分：

1. 组级计划状态：`训练计划已确认`；
2. 单任务检查状态：`自动检查通过`、`待调整`、`已纳入当前计划`；
3. 题目审核状态：`待人工审核`、`审核通过`；
4. 发布状态：`已发布`。

汇总文案使用“`N 个训练任务已通过检查`”。主工作区使用“第 N 版”，内部 `Revision N` 只在审核记录和追溯区显示。

### 17.5 回归要求

1. 构造缺少当前 Assessment Bundle 的待审 Revision；
2. 确认检查摘要显示不完整；
3. 确认提醒接受按钮不可用；
4. 确认审核通过不可用；
5. 退回录入端并完成保存、重新检查和重新提交；
6. 确认同一题目的新 Revision 恢复待确认和审核操作；
7. 确认撤回只追加审计事件，不创建内容 Revision。

## 十八、退回修订的页面恢复契约

### 18.1 退回成功后的页面行为

“确认退回”成功后，页面立即切换到同一 `draftId` 的录入状态，并携带结构化问题类型作为定位依据。用户不需要再次选择素材、训练计划或题目。

恢复 URL 必须保留：

```text
mode=plan-review
planId
materialVersionId
draftId
repair=<issueType>
```

`repair` 只用于页面定位，不是新的领域状态。真实退回要求始终读取当前 Draft 所绑定的 `ResourceReviewDecision.returnRequest`。

### 18.2 录入端首层恢复卡

被退回题目的首层显示：

```text
该题已退回修改
问题类型：……
具体问题：……
修改要求：……
当前进度：……
```

卡片只提供一个与当前阶段匹配的主动作：

| 阶段 | 主动作 |
| --- | --- |
| 待修改 / 修改待保存 | 保存本次修改 |
| 已保存，待重新检查 / 检查未通过 | 重新检查题目 |
| 可重新提交 | 提交最终确认 |

页面已有的保存、检查和提交 Command 保持不变；恢复卡只解释并导航，不另建一套写入逻辑。

### 18.2.1 基础结构检查与完整质量检查的展示层级

题目录入端保留两层检查，但页面必须合并解释，不能分别显示两个容易相互误解的“通过 / 有问题”结论：

1. **基础结构检查**只判断必填字段、数据结构和最低提交条件，不代表题目质量已经完成检查；
2. **完整质量检查**在基础结构通过后继续判断材料依据、能力目标、题目区分度、难度、作答范围和评分标准；
3. 完整质量检查存在提醒时，顶部统一显示“基础结构通过，N 项质量提醒待处理”，不得只突出绿色“结构检查通过”；
4. 完整质量检查卡片必须直接显示“N 项通过 · M 项待处理”，并在同一卡片内展示具体提醒；
5. 只有完整质量检查无阻断、无待处理提醒且记录绑定当前 Revision 时，才显示“质量检查通过”；
6. 页面术语固定为“基础结构检查”和“完整质量检查”，不再混用“自动结构检查”“题目质量检查”“完整检查”等近义名称。

因此，基础结构通过而完整质量检查仍有提醒是合法中间状态，但页面必须呈现为一个清晰的合并结论，而不是两个看似矛盾的状态。

### 18.3 自动定位

页面加载被退回 Draft 后只执行一次自动定位：

1. 先展开包含目标字段的编辑区；
2. 滚动到目标字段；
3. 使用单层高亮提示目标；
4. 聚焦可编辑控件；
5. 不覆盖用户已经输入的内容。

自动定位失败时显示“未找到指定修改位置”，但继续保留当前 Draft 和退回要求。

### 18.4 重新提交

重新提交前统一判断：

```text
!dirty
&& currentValidation.passed
&& currentAssessment.status === 'current'
&& blockerCount === 0
```

不满足时，提交按钮不可用并明确指出缺少“保存”还是“重新检查”。满足后提交当前 Draft，不创建新的同题 Draft。

### 18.5 审核端恢复压缩

检查记录不完整时，审核端默认折叠检查详情和待确认事项，只保留：

1. 缺失依据的摘要；
2. “退回录入修改”；
3. 审核记录入口。

审核端不得用多张黄色卡片重复解释同一恢复动作。

## 十九、P2 展示层收口

本节只统一页面身份、审核信息层级和提交元数据，不改变 Draft、Revision、
Assessment、Human Review 或 Publication 的领域状态。

### 19.1 页面身份固定，题目状态局部呈现

`question-resource-workbench` 是同一个批次题目工作台。用户在右侧批次列表选择草稿、
待审核、待发布或已发布题目，只是在同一工作台内切换当前处理对象，不是页面跳转。

因此页面级标题必须固定：

| 路由模式 | 页面标题 |
| --- | --- |
| 批次录入、修改、审核与发布工作台 | 题目资源工作台 |
| 非批次的独立录入入口 | 题目录入工作台 |

题目生命周期只允许在局部区域表达：

| 当前题目状态 | 主内容区标题 |
| --- | --- |
| 草稿、检查失败、退回修改 | 题目 N · 修改与提交 |
| 待人工审核 | 题目 N · 人工审核 |
| 审核通过、待发布 | 题目 N · 发布准备 |
| 发布部分完成 | 题目 N · 发布恢复 |
| 已发布 | 题目 N · 已发布 |
| 不采用或归档 | 题目 N · 审核记录 |

右侧批次导航继续通过状态标签显示题目状态。选择题目、切换页签、刷新或通过深链恢复时，
不得改变页面级标题，不得让用户误以为离开了当前工作台。只有进入不同路由、不同领域对象
的独立管理页面时，才允许更换页面名称。

### 19.2 录入信息进一步折叠

审核端首层优先展示：

1. 题目内容；
2. 评分规则；
3. 关联材料摘要；
4. 待确认事项与审核决策。

训练目标、具体训练点、观察目标、学生任务、难度与最低字数统一放入默认折叠的
“录入信息”。完整自动检查明细统一放入默认折叠的“录入检查记录”。

待确认事项不得因为检查记录折叠而隐藏；审核者仍需在首层看到并逐项作出决定。

### 19.3 审核提交元数据

进入最终确认及后续发布阶段后，所有审核页签顶部持续显示：

1. 题目版本；
2. 提交人；
3. 提交时间；
4. 当前审核或发布状态。

提交人和提交时间读取当前 Draft 的正式提交记录。缺失时必须明确显示“系统”或
“未记录”，不得展示内部 ID，也不得由页面当前时间推断。

### 19.4 验收

1. 批次工作台在修改、待审、待发布、发布恢复、已发布和归档状态下保持同一页面标题；
2. 页面身份与题目局部状态标题分别由统一展示状态解析函数生成；
3. 审核内容首层不再同时展开训练目标、作答要求和完整检查明细；
4. “录入信息”和“录入检查记录”可以独立展开与收起；
5. 待确认事项在检查记录折叠时仍然可见；
6. 内容审核、学生预览和审核记录均能看到相同的提交人和提交时间；
7. 状态映射回归必须覆盖稳定页面身份和全部题目局部状态标题。

## 二十、2026-07-30 错误提示、退回定位与状态口径补强

### 20.1 退回问题必须直接定位字段

结构化退回类型必须直接映射到页面字段或受控设置区，不得先转换为质量检查类别，
再由质量检查类别猜测修改位置。

唯一映射如下：

| 退回问题类型 | 首选定位 |
| --- | --- |
| `question_expression` | 题干 |
| `ability_target` | 训练目标；由 Plan 管理时进入训练计划调整入口 |
| `difficulty` | 难度；由 Plan 管理时进入训练计划调整入口 |
| `rubric` | 评分标准 |
| `answer_scope` | 最低作答与答案接受范围 |
| `student_presentation` | 题型、作答格式与题干 |
| `other` | 不自动定位，明确提示按退回要求人工查找 |

该映射必须由页面恢复、退回卡片和端到端测试共同消费。定位失败必须显示错误提示，
不得静默停留在原位置。

### 20.2 无效题目链接不得静默回退

URL 明确携带 `draftId`，但当前批次不存在该题目时：

1. 不得无提示地把用户切换到批次第一题；
2. 如批次仍有题目，可打开第一题，但必须提示“原题目不存在或已删除，已打开题目 N”；
3. 如批次为空，显示空状态和原题目不可用提示；
4. 提示必须在刷新、浏览器返回和外部深链进入时保持一致。

该规则用于防止用户误把另一题当作原题继续修改。

### 20.3 批次统计与导航命名

统一资源生产工作台题目区的状态统计必须严格按生命周期计算：

1. `本批题目（N）` 是批次总量基准，不属于可相加的生命周期状态桶；
2. 批次中的每道题必须且只能进入以下一个状态桶：
   `待处理`、`待最终确认`、`已确认（待发布）`、`已发布`；
3. `待处理` 统计 `drafted`、`validation_failed`、`revision_required` 等尚未进入人工审核的题目；
4. `待最终确认` 只统计 `pending_review`；
5. `已确认（待发布）` 统计 `reviewed`，以及已形成审核决定但正式发布尚未完整结束的
   `publication_incomplete`；
6. `已发布` 只统计已存在有效正式资源关联的题目；
7. 同一道题同时存在多个可推导信号时，按
   `已发布 > 已确认（待发布） > 待最终确认 > 待处理`
   的优先级归入唯一状态桶；
8. 四个状态桶必须满足以下不变量：

```text
待处理 + 待最终确认 + 已确认（待发布） + 已发布 = 本批题目总数
```

9. 包含多种状态的右侧导航统一命名为“本批题目”，不得称为“本批待审核题目”。

状态统计、列表状态标签和页面标题必须消费同一份展示状态投影。
页面不得分别对 Draft、Review 和 Formal Resource 记录做无去重累加，否则同一道题会同时进入
多个统计项，造成状态总和大于批次总量。

### 20.4 提醒事项的时态命名

提醒区标题必须反映当前是否仍需要审核者操作：

| 当前状态 | 标题 |
| --- | --- |
| `pending_review` 且存在未决提醒 | `待确认事项（N）` |
| `reviewed`、`published` 或提醒均已有决定 | `提醒处理记录（N）` |

已接受的提醒不得继续显示为“待确认事项”。历史决定只读展示，不再提示用户继续确认，
也不再显示“完成后才可审核通过”等进行中文案。

### 20.5 P1 端到端验收

至少增加以下回归：

```text
待最终确认
→ 选择结构化退回问题类型
→ 退回同一 draftId
→ 自动定位到该类型对应的准确字段
→ 修改并保存一个新 Revision
→ 重新检查
→ 同一 draftId 再次提交最终确认
```

同时覆盖：

1. 每一种退回问题类型的目标字段；
2. 失效 `draftId` 的显式提示；
3. 混合状态批次中“待最终确认”计数只包含 `pending_review`；
4. 已处理提醒在审核通过和发布后显示为“提醒处理记录”。

### 20.6 批次统计驻顶边界

统一资源生产工作台题目区滚动时只驻顶批次总量标签和四个互斥生命周期状态桶：

1. `本批题目（N）`；
2. `待处理`；
3. `待最终确认`；
4. `已确认（待发布）`；
5. `已发布`。

其中 `本批题目（N）` 只表达总量基准；四个状态桶的数字相加必须等于 `N`，不得把总量本身
再次参与求和。

“批次处理概览”及其阻断、提醒、待复检、重复修改、处理耗时等辅助信息不得进入驻顶容器，
必须随页面正文正常滚动。该边界用于保证审核人员持续掌握批次主状态，同时避免辅助统计长期占用
垂直空间、遮挡当前题目和审核操作。

驻顶容器必须满足：

1. 只消费批次总量和四个互斥生命周期状态桶，不复制批次处理概览；
2. 使用不透明页面背景、明确分隔线和稳定层级，滚动时不得与正文叠加；
3. 状态统计、题目列表标签和页面标题继续消费同一份展示状态投影；
4. 桌面端和窄屏下均不得因数字、标签或动态状态变化改变容器高度；
5. 自动化验收必须覆盖四个状态桶求和等于批次总量的不变量；
6. 浏览器验收必须确认“批次处理概览”不位于任何 `sticky` 容器内。

### 20.7 审核与发布步骤固定外显

题目进入检查、确认与发布流程后，页面必须固定外显同一条三步路径：

1. `1 题目检查`；
2. `2 最终确认`；
3. `3 正式发布`。

前台三步只用于降低用户理解负担，不改变底层领域边界：

| 前台操作 | 独立领域 Command | 结果 |
| --- | --- | --- |
| 提交最终确认 | `submitQuestionForHumanReview` | 当前 Revision 进入 `pending_review` |
| 确认通过 | `recordHumanReviewDecision` | 为当前 Revision 记录 Human Review Decision |
| 发布正式题目 | `freezeAndPublishQuestion` | Freeze 并幂等完成正式发布 |
| 重试发布 | `resumeQuestionPublication` | 复用既有审核与正式化结果，只补齐失败阶段 |

不得将以上 Command 合并为一个无法辨认中间结果的 Handler。即使单人快捷模式提供
`确认通过并发布`，内部也必须按顺序执行审核决定与正式发布；审核成功但发布失败时，
页面显示 `审核已通过，发布未完成` 和 `重试发布`，不得退回待审核状态或重复生成
Human Review Decision。

步骤导航只表达流程位置，不承担提交、审核或发布操作。当前进行中的步骤使用蓝色数字与蓝色标题，
非当前步骤统一使用灰色；颜色之外仍必须保留步骤编号和中文名称。当前步骤对应的按钮与说明
继续展示在步骤导航下方，不得把操作按钮嵌入步骤导航。

首次检查、保存后重新检查、退回修改后重新检查都属于步骤 1，不得另外渲染一套“基础结构检查”
步骤标题。步骤 1 同时承载基础结构检查和完整质量检查的操作入口；检查层级仍按 18.2.1 定义，
但流程导航统一使用面向用户的名称“题目检查”。

步骤 2 合并前台原有的“提交题目人工审核”和“题目人工审核”表达。它可以包含提交当前 Revision、
查看内容与学生预览、确认已处理提醒、填写审核说明、退回修改和形成审核决定，但不得在审核期间
直接编辑正式字段。退回修改后必须回到同一 Draft 的步骤 1，修改、保存并重新检查后才能再次进入
步骤 2。

步骤 3 表达正式发布阶段。审核通过但尚未发布时，步骤 3 为蓝色当前态，页面显示
`已确认，待发布` 和 `发布正式题目`；发布失败时继续停留在步骤 3，并显示可单独执行的
`重试发布`。正式发布完成后页面不再存在蓝色当前步骤，步骤 3 改为绿色 `已发布`，且不得再次
显示发布按钮。

页面不得在步骤导航下方再次重复当前步骤的编号和标题。生命周期到步骤的映射必须继续消费
统一状态计算：

| 生命周期状态 | 当前外显步骤 |
| --- | --- |
| 首次检查、修改未保存、检查失效、提醒待处理或待重新检查 | 1 |
| 录入检查完成、尚未提交最终确认 | 2 |
| `pending_review` 或待形成审核决定 | 2 |
| `reviewed`、`approved`、`frozen`、发布处理中或 `publication_incomplete` | 3 |
| `published` | 无当前步骤；步骤 3 显示绿色 `已发布` |
| `changes_requested` 或已退回修改 | 1 |

#### 20.7.1 统一状态投影函数

步骤条、页面状态文案、主按钮、按钮禁用状态、题目列表状态标签和刷新恢复不得分别拼装生命周期。
领域层必须提供一个统一状态投影函数，并由所有展示和操作入口共同消费：

```ts
type QuestionWorkflowVisibleStep =
  | 'question_check'
  | 'final_confirmation'
  | 'formal_publication'
  | 'published';

type QuestionWorkflowSubstate =
  | 'dirty'
  | 'check_required'
  | 'warning_pending'
  | 'ready_to_submit'
  | 'pending_review'
  | 'approved'
  | 'publishing'
  | 'publication_incomplete'
  | 'published';

type QuestionWorkflowPrimaryAction =
  | 'save_and_recheck'
  | 'submit_final_confirmation'
  | 'record_review_decision'
  | 'publish'
  | 'resume_publication'
  | null;

type QuestionWorkflowProjection = {
  step: QuestionWorkflowVisibleStep;
  substate: QuestionWorkflowSubstate;
  message: string;
  primaryAction: QuestionWorkflowPrimaryAction;
};

function resolveQuestionWorkflowProjection(input: {
  draft: QuestionDraft;
  isDirty: boolean;
  assessmentState: CurrentAssessmentState;
  unresolvedWarningCount: number;
  review: HumanReviewDecision | null;
  publication: PublicationResult | null;
}): QuestionWorkflowProjection;
```

`isDirty` 必须来自当前页面编辑缓冲区，不能仅根据已保存 Draft 推断。
`assessmentState` 必须使用 5.4 定义的当前有效 Assessment 唯一计算结果，不能只判断是否存在
Assessment。统一投影函数必须成为步骤条、页面标题、主提示、主操作、状态标签和刷新恢复的唯一
状态来源；组件不得再维护平行布尔判断。

#### 20.7.2 最终确认的内部子状态

步骤 2 固定显示 `最终确认`，但内部必须区分两个子状态：

| 子状态 | 主提示 | 页面内容与操作 |
| --- | --- | --- |
| `ready_to_submit` | 当前题目已完成检查，等待最终确认 | 显示检查摘要和 `提交最终确认` |
| `pending_review` | 当前 Revision 正在最终确认 | 正式字段只读，显示内容确认、学生预览、审核记录以及 `确认通过 / 退回修改` |

两个子状态的步骤条都高亮步骤 2，但不得共用同一主按钮，也不得让尚未提交的题目显示审核决定操作。
从 `pending_review` 退回后，统一投影必须回到步骤 1，并保持同一 Draft 链路。

#### 20.7.3 正式发布的状态文案

步骤 3 固定显示 `正式发布`，但主状态文案和操作必须按发布生命周期区分：

| 子状态 | 固定主提示 | 主操作 |
| --- | --- | --- |
| `approved` / `reviewed` | 已确认，待发布 | 发布正式题目 |
| `frozen` / `publishing` | 正在发布 | 无重复提交入口；显示进行中状态 |
| `publication_incomplete` | 审核已通过，发布未完成 | 重试发布 |
| `published` | 已发布 | 无 |

发布失败不得回退为 `pending_review`，也不得重新创建 Human Review Decision。`published` 为流程完成态，
步骤 3 使用绿色完成样式；其余步骤 3 子状态使用蓝色当前态或明确的失败恢复状态。

#### 20.7.4 最终前台映射

| 当前状态 | 步骤 | 主提示 | 主操作 |
| --- | --- | --- | --- |
| 草稿、`dirty`、检查失效、提醒待处理 | 1 | 当前题目需要完成检查 | 保存并重新检查 |
| 检查完成但未提交 | 2 | 当前题目已完成检查，等待最终确认 | 提交最终确认 |
| `pending_review` | 2 | 当前 Revision 正在最终确认 | 确认通过 / 退回修改 |
| `approved` / `reviewed` | 3 | 已确认，待发布 | 发布正式题目 |
| `publication_incomplete` | 3 | 审核已通过，发布未完成 | 重试发布 |
| `published` | 完成 | 已发布 | 无 |

用户可见文案统一为：

| 旧文案 | 新文案 |
| --- | --- |
| 提交题目人工审核 | 提交最终确认 |
| 题目人工审核 | 最终确认 |
| 审核通过（待发布） | 已确认，待发布 |
| 发布准备检查 | 正式发布 |
| 已完成发布 | 已发布 |

领域模型、审计记录和工程 Command 继续使用 Human Review、Freeze、Formal Resource 等正式术语，
不得因页面文案调整而改写历史数据或混淆状态边界。

验收至少覆盖：

1. 用户不再看到两个连续且含义相近的人工审核步骤；
2. 修改后步骤 1 高亮，重新检查通过后切换到步骤 2；
3. 提交最终确认后仍停留在步骤 2，并能形成独立审核决定；
4. 审核通过后切换到步骤 3，发布失败可单独重试；
5. 退回修改后回到同一 Draft 的步骤 1，不创建重复草稿；
6. 发布成功后步骤 3 显示绿色 `已发布`，页面不存在蓝色当前步骤和重复发布入口；
7. 刷新页面后仍能根据当前 Draft、Human Review 与发布状态恢复同一流程位置；
8. 步骤条、页面标题、主提示、按钮、列表标签和刷新恢复消费同一个
   `QuestionWorkflowProjection`；
9. `ready_to_submit` 与 `pending_review` 同属步骤 2，但页面操作严格区分；
10. `approved`、`publishing`、`publication_incomplete` 和 `published` 使用各自固定文案与操作；
11. 提交、审核决定和发布分别形成可追溯记录，多人模式未来可恢复更细的角色分工。

#### 20.7.5 完成态与提醒待处理态的操作边界

`published` 是终态。页面进入该状态后，不得继续使用当前 Draft Revision 的 Assessment、
训练计划差异或发布准备清单反向判定已发布结果，也不得再显示 `发布准备`、`3/4 项完成`、
当前 Revision 阻断或修复入口。历史检查结果、审核决定与发布过程只允许在检查记录、审核记录
或发布记录中只读查看。正式资源如需调整，必须先基于当前正式版本生成新版 Candidate，采用后创建新的修订链路；不得恢复或直接修改已发布版本。

存在质量提醒且录入人员尚未完成处理说明时，页面处于 `warning_pending`。该状态不能只展示提醒
和理由输入框，还必须持续外显明确的下一步动作：

1. 每项提醒提供 `定位修改`，允许用户返回对应字段修正；
2. 若选择保留当前设置，每项提醒必须填写处理理由；
3. 页面始终显示 `保留当前设置并提交最终确认`；
4. 理由未填写完整、Assessment 已失效或当前内容未保存时，该按钮保持禁用，并在按钮附近说明
   具体原因；
5. 理由填写完整后，统一状态投影切换到 `ready_to_submit`，按钮启用并提交同一 Draft Revision；
6. 禁止因为提醒待处理而隐藏主操作，也禁止通过提交动作创建新的平行 Draft。

步骤条、状态提示和按钮可用性必须共同消费 `QuestionWorkflowProjection` 与当前 Assessment 状态。
不得出现“题目已经发布但发布准备未完成”，也不得出现“系统要求处理提醒但页面没有处理或提交
入口”。

### 20.8 审核决策区信息唯一来源

审核期间的提交人、提交时间、题目版本和审核状态统一由页面顶部提交信息区展示。审核决策区
不得再次复制提交人和提交时间，避免同一事实在页面中出现多个展示位置并产生更新错位。

审核说明字段保留标题 `审核说明（可选）` 和输入框占位文案 `可填写审核说明`，不再附加
同义辅助句。审核说明默认空白，只记录审核者主动填写的补充意见，不得由系统预填审核结论。

验收必须确认：

1. 同一题目页面只出现一组提交人和提交时间；
2. 审核决策区仍可正常填写审核说明；
3. 删除重复信息不影响提醒确认、退回修改、审核通过和发布状态；
4. 顶部提交信息继续绑定当前 Draft Revision，不读取历史 Revision 的提交元数据。

### 20.9 质量问题展示投影

录入端的质量检查必须区分内部问题模型与用户操作文案。内部继续保留稳定的
`issue code`、`check`、规则版本和原始判断依据；页面不得直接展示模型判断语言，
而应统一投影为“问题标题、当前设置、原因、建议、可能涉及区域和定位操作”。

单个质量问题默认结构固定为：

```text
题目难度可能需要调整

当前设置：基础难度
原因：题目包含多个分析要求，可能超过当前训练目标。
建议：调整难度设置，或减少题目的分析任务。
可能涉及：训练设置 / 题目要求

[定位修改] [查看示例]
```

展示层必须遵守：

1. 检查摘要只显示“N 项通过 · M 项需要处理”，不重复展示“当前优先处理”；
2. 不单独展示“修改位置”，改为轻量文案“可能涉及：A / B”，实际字段由“定位修改”负责；
3. 参考写法默认折叠为“查看示例”，不得占据问题卡片首屏；
4. 删除“改到什么程度算完成”，用户以保存并重新检查后的最新 Assessment 为完成依据；
5. 问题标题使用面向人的操作语言，例如 `difficulty_alignment_warning` 在页面显示为
   “题目难度可能需要调整”；
6. 原因只解释为什么需要关注，不输出 `Rubric 复杂度`、规则代码或模型内部置信判断；
7. 建议只给出一条可执行方向，详细示例按需展开；
8. `定位修改`优先聚焦首要字段；同一问题涉及多个区域时，不同时展开多个编辑区；
9. 多个问题仍消费同一修复队列和问题状态，不因展示压缩改变检查、保存、复检和关闭语义。
10. 难度一致性提醒必须明确指出偏差方向：基础难度的作答要求偏多，或进阶难度的作答要求偏少；不得向用户展示 `Rubric 复杂度可能不一致`等内部判断语言。
11. 页面必须按稳定的 `warning.check` 投影用户文案，不得直接依赖已持久化的历史 `warning.message`；历史 Assessment 在不重新检查的情况下也必须使用当前展示文案。

验收至少确认：

1. 单问题卡片首屏不再出现“当前优先处理”“修改位置”“参考写法”和“改到什么程度算完成”；
2. “查看示例”默认收起，点击后可展开，再次点击可收起；
3. “定位修改”仍准确聚焦原 Issue 对应的字段；
4. 页面不展示内部 Issue Code，但保存、复检和问题关闭继续使用原 Code；
5. 常见单问题内容区域在桌面端明显缩短，不再形成长篇修改教程。

### 20.10 录入端任务级题目状态入口

素材资源录入端不得通过顶部汇总数字承载题目查看和处理入口。顶部只展示待人工审核、发布未完成
和已发布的只读数量；题目状态、查看和后续处理动作必须落到对应训练任务卡片。

训练任务与题目 Draft、正式版本统一通过 `observationTaskPlanId` 关联。任务卡显示的计划状态与
题目生命周期状态是两个独立维度，不得用“已纳入当前计划”代替“题目已发布”，也不得因题目尚未
生成而把训练任务误报为需要修改。

任务卡进入审核或发布平台时必须携带当前 `materialObservationPlanId`、`materialVersionId` 和
可用的 `draftId`。该入口只恢复当前题目上下文，不创建新 Draft、不重复提交审核，也不改变
Publication 状态。

### 20.11 无问题通过态压缩

结构检查通过且不存在任何问题时，页面不得继续展示大面积绿色结果卡片，也不重复说明
“基础结构检查通过”或“没有阻断项”。通过结果应由步骤状态、检查项状态和下一步操作是否可用
共同表达，用户可以直接继续后续流程。

以下情况仍必须展示结果区域：

1. 结构检查未通过；
2. 检查通过但仍包含需要人工处理或确认的提醒；
3. 检查结果已因内容修改而失效；
4. 检查服务失败或完整质量检查尚未形成。

验收必须确认：无问题通过后绿色成功卡片消失，后续操作保持可用；存在提醒或阻断时问题提示
仍正常展示，且检查、保存、复检与提交逻辑不发生变化。

### 20.12 异步检查操作反馈

`检查题目`、`继续完成检查`和`重新检查题目`均为异步业务操作。用户触发后，按钮不得只切换为
静态禁用态，否则用户无法判断点击是否生效、系统是否仍在处理。

检查进行期间必须同时满足：

1. 按钮保持原位置和稳定尺寸，不因文案或图标变化造成布局跳动；
2. 按钮显示旋转加载图标，并根据当前语义显示`正在检查题目`或`正在完成检查`；
3. 按钮设置`aria-busy="true"`，鼠标使用等待状态；
4. 按钮在请求结束前保持不可重复触发，防止生成重复 Validation、Assessment 或并发写入；
5. 加载态使用蓝色执行语义，不得显示成普通灰色禁用态或绿色完成态；
6. 成功后根据最新持久化结果刷新检查摘要、步骤和主操作；
7. 失败后必须在`finally`语义下恢复按钮可用状态，并继续显示明确错误信息，允许用户重试；
8. 页面刷新、题目切换或组件卸载后，过期请求结果不得覆盖较新的题目状态。

按钮禁用原因必须区分：

| 状态 | 页面表现 |
| --- | --- |
| 操作正在执行 | 蓝色 Loading、旋转图标、进行中文案、禁止重复点击 |
| 当前生命周期不允许检查 | 中性灰色禁用态，并由邻近状态文案说明原因 |
| 检查成功 | 移除 Loading，根据统一工作流投影进入下一状态 |
| 检查失败 | 移除 Loading，恢复重试入口并展示失败原因 |

验收至少覆盖：

1. 点击检查后立即出现 Loading，而不是只变灰；
2. 连续点击不会发起第二个检查命令；
3. 首次检查显示`正在检查题目`；
4. 结构结果已存在但完整质量记录待补齐时显示`正在完成检查`；
5. 成功、业务失败和异常抛出三种路径都会结束 Loading；
6. Loading 期间按钮宽度、高度和周边布局不发生变化；
7. Production Build、题目工作台 Command E2E 与工作流投影专项继续通过。

### 20.13 完整检查记录的选择与恢复

同一 Draft Revision 与 Validation 下可能因历史重试、语义服务失败或比较上下文变化，保留多条
确定性检查、语义检查与合并结果。页面不得简单选择时间最新的确定性检查，再据此判断完整检查
是否存在。

当前完整检查记录必须按以下规则解析：

1. 只读取绑定当前 `draftId`、Draft Revision、Validation 与规则版本的记录；
2. 在所有匹配记录中，优先选择已经形成 `completed` 语义检查和非
   `semantic_unavailable` Bundle 的完整链；
3. 较新的孤立确定性检查不得遮蔽同一 Revision 下已经完成的完整检查链；
4. 只有失败或不可用检查链时，页面可以展示“完整检查未完成”，但再次执行必须真正重试语义
   检查，不得幂等返回失败 Bundle；
5. 页面上下文、批次统计、提交门禁与发布门禁必须消费同一条首选检查链；
6. 当前 Draft 正式字段未变化时，同批其他题目的增删改不得让已审核或已发布题目退回
   “继续完成检查”；
7. 检查成功刷新后，主操作必须进入下一生命周期；不得继续原地显示“继续完成检查”。

验收至少覆盖：

1. 同一 Revision 同时存在“较新孤立记录”和“较旧完整链”时，页面恢复完整链；
2. 语义服务失败后点击重试可生成新的完整链；
3. 刷新页面不会无条件创建新的确定性检查记录；
4. 已审核或已发布题目不会因同批其他题变化退回检查阶段；
5. 点击“继续完成检查”成功后，按钮不再原地出现。

### 20.14 完整检查命令的成功边界

`继续完成检查`不得以“结构检查已经通过”作为成功条件。命令只有在当前 Draft Revision 下同时
形成已完成的语义检查记录和可用的合并 Bundle 后，才可以返回成功。

页面、主操作和提交门禁必须统一读取 API 输出的 `qualityCheckState`：

```ts
type PersistedQuestionQualityCheckState =
  | 'missing'
  | 'incomplete'
  | 'complete';
```

其中：

1. `missing` 表示当前 Revision 尚无完整检查链；
2. `incomplete` 表示已有部分记录，但语义检查失败、超时或 Bundle 不可用；
3. `complete` 表示语义检查已完成，且 Bundle 可用于当前 Revision。

当底层只返回 `semantic_unavailable` 等部分结果时，命令必须保持 Loading 并按有限次数重试；
重试后仍未完成，应返回可重试错误，不得显示成功提示，也不得在刷新后再次无解释地回到
`继续完成检查`。

`assessmentState` 仅说明确定性检查是否对应当前 Revision，不得单独作为完整质量检查已经完成的
依据。

### 20.15 页面与提交命令的检查上下文一致性

页面展示“全部质量检查通过”、步骤进入“最终确认”以及提交命令放行，必须消费同一个当前完整
检查上下文选择结果。禁止页面与 Command 分别使用不同的查找逻辑。

统一选择器必须遵守：

1. 同时扫描当前 Draft Revision、Validation、规则版本下的全部确定性检查、语义检查与 Bundle；
2. 只把 `completed` 语义检查和可用 Bundle 组成的完整链视为可提交上下文；
3. 较新的孤立确定性记录、失败语义记录或缺失 Bundle 的重试记录，不得遮蔽同 Revision 下较早
   形成的完整链；
4. 页面、批次统计、`qualityCheckState`、提交最终确认和发布前置检查必须复用同一选择器；
5. 找不到完整链时，页面不得展示“全部质量检查通过”或可用的提交主操作；
6. 已经进入 `pending_review` 或 `reviewed` 的同一 Draft Revision，再次执行提交命令应幂等返回
   当前状态，不得先以旧检查记录阻断；
7. 选择器返回的检查身份必须包含确定性 Assessment、语义 Assessment 与 Bundle 身份，不能只
   返回确定性检查的当前性。

以下状态必须被识别为“完整链存在”：

```text
同一 Revision：
  较旧记录 = Deterministic + completed Semantic + usable Bundle
  较新记录 = Deterministic only

结果：
  选择较旧完整链
  页面显示检查完成
  提交最终确认可以继续
```

不得把上例误判为：

```text
Current semantic assessment result is required.
```

### 20.16 Command 成功与页面刷新结果分离

保存、检查、提交最终确认、审核决定和发布均可能出现“领域命令已成功，但随后页面刷新失败”的
部分成功场景。交互层必须分开处理：

1. 领域命令成功后，不得因为刷新失败而显示“提交失败”；
2. 刷新失败时显示“操作已完成，页面状态刷新失败，请刷新查看最新状态”；
3. 用户刷新或重试时，命令必须依据幂等身份恢复已有结果，不得重复创建审核记录、Revision 或
   正式版本；
4. 每个主命令使用同步执行锁，防止 React 状态尚未刷新时的快速双击发起第二个请求；
5. 执行期间保持明确 Loading，完成后才释放执行锁；
6. 错误提示优先使用中文领域文案；英文内部错误仅允许折叠在“技术信息”中。

验收至少覆盖：

1. 同一 Revision 存在“完整链 + 更新的孤立记录”时，页面和提交命令选择同一完整链；
2. 重复提交最终确认只形成一个 `pending_review` 转换；
3. 命令成功、刷新失败时不误报提交失败；
4. 快速双击只发起一个领域命令；
5. 刷新后能够恢复已成功的生命周期状态。

### 20.17 全局异步主命令反馈规范

保存、检查、提交最终确认、撤回、退回修改、形成审核决定、正式发布和发布重试等会改变业务状态
的主命令，必须提供即时、可辨认且与当前命令绑定的执行反馈。用户点击后不得只把按钮切换为
静态灰色禁用态，也不得等待领域命令或页面刷新完成后才改变按钮表现。

所有异步主命令统一遵守以下规则：

1. 有效点击被接收后，当前按钮必须在下一次可见渲染中立即进入 Loading；
2. Loading 必须同时包含旋转图标、与命令对应的进行中文案、`aria-busy="true"` 和等待光标；
3. 进行中文案必须明确当前动作，例如`正在保存`、`正在提交最终确认`、`正在确认通过`、
   `正在退回`、`正在发布`或`正在重试发布`，不得统一显示含义模糊的`处理中`；
4. 只有当前被触发的按钮显示 Loading；同组其他互斥动作可以暂时禁用，但不得同时显示为正在
   执行，避免用户误判系统并行执行多个命令；
5. Loading 使用蓝色执行语义并保持按钮原有尺寸，不得退化为普通灰色禁用态，不得因图标或
   文案变化引起布局跳动；
6. React 状态更新之外必须设置同步执行锁；在首个请求结束前，快速双击或连续触发不得发起第二
   个领域命令；
7. 领域命令成功、业务失败、异常抛出和命令成功但页面刷新失败四条路径都必须在 `finally`
   语义下释放执行锁并结束 Loading；
8. 命令成功后刷新失败时，页面提示`操作已完成，页面状态刷新失败，请刷新查看最新状态`，
   不得把已成功的领域命令误报为失败；
9. 过期请求不得覆盖题目切换、页面刷新或较新命令已经恢复的状态；
10. 普通数据刷新仍遵守独立刷新反馈规范；本节不要求把一次性刷新动画扩展为持续 Loading。

实现层必须维护独立的当前命令身份，例如：

```ts
type QuestionWorkbenchCommand =
  | 'save_draft'
  | 'validate_draft'
  | 'submit_final_confirmation'
  | 'withdraw_review'
  | 'approve_review'
  | 'return_for_revision'
  | 'publish_question'
  | 'retry_publication';
```

页面可以使用一个全局互斥执行锁保护写命令，但不得只使用单一 `busy: boolean` 推导所有按钮的
视觉状态。按钮 Loading 文案和 `aria-busy` 必须由当前命令身份决定。

状态表现统一为：

| 状态 | 当前按钮 | 同组其他按钮 |
| --- | --- | --- |
| 命令可执行 | 正常主或次按钮 | 正常 |
| 当前命令执行中 | 蓝色 Loading、旋转图标、进行中文案 | 暂时禁用，不显示 Loading |
| 生命周期不允许执行 | 中性灰色禁用态，邻近位置说明原因 | 按各自门禁处理 |
| 命令成功 | 结束 Loading，按统一工作流投影进入新状态 | 恢复或随新状态变化 |
| 命令失败 | 结束 Loading，恢复重试并展示领域错误 | 恢复 |
| 命令成功但刷新失败 | 结束 Loading，提示刷新恢复 | 不重复执行原命令 |

验收至少覆盖：

1. 点击每个异步主命令后立即看到对应 Loading 文案；
2. 同一时刻只有一个按钮显示正在执行；
3. 快速双击只产生一次领域写入；
4. 成功、业务失败、异常和刷新失败都会结束 Loading；
5. Loading 前后按钮宽度、高度及周边布局保持稳定；
6. 提交、审核与发布等生命周期命令完成后，页面不再停留在旧操作状态；
7. Command E2E 验证重复保存、检查、提交、审核和发布不会产生重复 Revision、Review 或正式
   资源。

### 交互补充：显式接受质量提醒

单人模式中，质量提醒出现后自动编排必须停止。用户选择“保留当前题目”后，必须在轻量确认层为
每个 warning code 选择结构化理由；只有“确认保留并发布”才能把当前 Revision、当前 Assessment
和逐项理由写入审计记录，并从已完成阶段继续确认与发布。执行时必须立即显示“正在确认并发布…”
和旋转图标；失败后恢复可重试状态并在操作区附近展示错误，禁止静默禁用、自动接受提醒、用固定
理由批量接受提醒或重复创建 Revision。结构和必填字段阻断不允许进入该确认层。
