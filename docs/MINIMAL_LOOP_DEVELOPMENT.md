# 最小闭环模块开发原则

## 1. 核心原则

本项目采用“最小闭环模块 -> 阶段功能 -> 产品能力”的递进开发方式。

产品不是一次性完成的，而是通过一个个可独立运行、可独立验收、可互相协同的最小功能模块逐步生长出来。

本项目不是页面驱动型开发，而是能力驱动型开发。页面只是产品能力的承载方式，真正的开发目标是让系统逐步具备可运行、可验证、可复用的学习 Runtime 能力。

## 2. 递进关系

### 最小闭环模块

最小闭环模块是产品能力的最小组成单位。

更准确地说，最小闭环模块是一个职责单一、输入输出明确、可以独立运行和验收，并能够产生明确系统作用或被下游消费的产品运行单元。

每个模块必须具备：

- 明确输入
- 明确处理逻辑
- 明确输出结果
- 可独立运行
- 可独立验收
- 可被其他模块调用或协同
- 不依赖大范围重构才能生效

最小闭环模块不是代码文件，也不是页面组件，而是一个能够完成独立产品动作的运行单元。

一个最小闭环模块只承担一个主要业务责任。

模块可以调用其他模块，但不能重新执行上游已经完成的判断。

模块输出必须有明确下游或验收用途。

如果一个模块同时负责诊断、评估、画像更新和下一步决策，应继续拆分。

### 阶段功能

若干个最小闭环模块组合后，形成一个阶段功能。

阶段功能不是页面集合，而是一个真实可运行的产品能力。

例如：

```text
题目输入模块
-> AI 诊断模块
-> 结构化结果展示模块
-> 诊断记录保存模块
-> 训练建议生成模块
```

这些模块组合后，形成“AI 诊断与训练建议闭环”。

### 产品能力

若干个阶段功能持续累积后，形成完整产品能力。

完整产品能力不是一次性设计完成，而是通过多个阶段逐步叠加形成。

例如：

```text
题目理解能力
-> 能力诊断能力
-> 训练建议能力
-> 能力证据能力
-> 学生画像能力
-> 复测验证能力
-> 长期成长追踪能力
```

这些能力持续组合，最终形成可长期运行的 AI 学习 Runtime。

## 3. Phase 开发规则

每个 Phase 只解决一个核心产品目标。

每个 Phase 建议拆分为 2 到 4 个小闭环，具体数量应根据阶段复杂度决定。

每个小闭环都必须能独立开发、独立运行、独立验收。

每个小闭环完成后，系统必须新增或完善一项可运行、可验证、可保存、可复用或可驱动下游的产品能力。

这里的“能力”指系统产品能力增量，不等于学生能力已经发生变化。

例如，作答有效性校验模块完成后，学生能力未必变化，但系统新增了识别无效答案、阻止错误诊断和输出 `insufficient_evidence` 的能力。

Phase 开发应遵循以下顺序：

```text
定义阶段目标
-> 确认核心模型与职责边界
-> 拆分最小闭环
-> 明确输入输出契约
-> 建立调试样例
-> 实现运行模块
-> 输出结构化结果
-> Debug / Build
-> 验收并冻结
-> 沉淀为可复用能力
```

如果某个 Phase 无法拆出可验收的小闭环，说明该 Phase 目标仍然过大或不够清晰。

核心模型增强后，应检查当前 Runtime 与未来 Phase 的一致性。

已经完成的历史 Phase 可以保留当时的最小实现，但必须标明其与最新长期协议的差异。

历史 Phase 是实现记录，不应因为长期模型演进而被自动重写。

## 4. 禁止事项

开发过程中禁止以下行为：

- 只做页面展示，但没有真实数据流
- 只完成代码结构，但用户无法感知结果
- 一个小闭环混入多个阶段目标
- 为当前小闭环大范围重构无关模块
- 破坏上一阶段已经验收通过的功能
- 把 AI 单次问答包装成产品能力
- 在没有保存、复用、协同机制的情况下宣称闭环完成
- 在输入、处理、输出不清晰的情况下进入开发
- 在没有可验证样例的情况下宣称模块稳定

## 5. 验收标准

一个最小闭环模块完成时，必须满足：

1. 用户或系统有明确触发动作。
2. 系统有明确处理流程。
3. 页面或数据层有明确结果输出。
4. 结果可以保存、复用或驱动下一步动作。
5. 不破坏已有功能。
6. 可以被单独验证。

如果一个模块只能在人工解释后才算完成，说明它尚未形成产品能力。

如果一个模块只能展示结果，但不能被下一步模块消费，说明它尚未形成闭环。

“保存、复用或驱动下一步动作”不要求三者同时成立。

有些最小模块只承担校验、转换、决策、展示或阻断作用。闭环的关键不是必须落库，而是结果必须产生明确系统作用，不能展示后失去意义。

## 6. 本项目的阶段能力方向

本项目后续能力按阶段逐步形成。

当前建议方向包括：

- 真实 AI 诊断能力
- 训练任务生成能力
- 复测验证能力
- 学生模型能力
- 长期成长追踪能力

这些阶段方向不是固定不变的排期，而是当前产品能力演进的建议路径。

每个阶段都必须围绕一个核心产品能力展开，不能偏离阶段目标。

当真实使用反馈表明阶段顺序需要调整时，应优先保持“最小闭环模块 -> 阶段功能 -> 产品能力”的开发原则，而不是机械执行原有阶段编号。

## 7. 与当前系统的关系

当前系统已经形成多个最小闭环模块：

```text
Question Metadata Generator
-> Metadata Validator
-> Diagnosis Agent
-> Ability Evidence Extractor
-> Weakness Ranking Agent
-> Training Plan Agent
-> Training Evidence / Retest Evidence Runtime
-> Student Ability Profile Agent
-> Personalized Next Task Agent
```

这些模块组合形成了当前可运行的学习成长链路：

当前已实现的最小链路：

```text
Question
-> Question Metadata
-> Validator
-> Diagnosis
-> Ability Evidence
-> Top Weakness
-> Training Plan
-> Training Evidence / Retest Evidence
-> Student Ability Profile
-> Personalized Next Task
```

这条链路反映的是当前工程已经跑通的最小 Runtime。

长期标准链路应逐步收敛为：

```text
Diagnosis Result
-> Ability Evidence
-> Evaluation Result
-> Profile Update Decision
-> Student Ability Profile
-> Personalized Next Task
```

也就是说，Training Evidence / Retest Evidence 不应长期直接修改 Student Ability Profile，而应先进入 Evaluation，再由 Profile Update Decision 决定是否追加证据、更新置信度、请求复测、更新状态或保持观察。

后续新增能力也应遵循同样原则。

例如，学生能力画像不应直接做成一个展示页，而应拆成：

```text
能力证据抽取
-> 证据聚合与评估
-> 画像更新决策
-> 能力状态更新
-> 弱点排序
-> 下一步建议
-> 画像展示
```

记录 Evidence 不等于更新长期能力状态。

只有当数据能够产生明确系统作用，例如被保存、复用、用于评估、触发复测、驱动下一步任务或支撑画像展示时，学生画像才算形成产品能力。

## 8. 开发结论

本项目不是页面驱动型开发，而是能力驱动型开发。

页面只是产品能力的承载方式。

真正的开发目标是让系统逐步具备：

- 输入能力
- 题目理解能力
- 诊断能力
- 记录能力
- 训练能力
- 复测能力
- 成长追踪能力

通过最小闭环模块持续积累，最终形成一个可长期运行的 AI 学习 Runtime。

本项目的长期开发主线可以概括为：

```text
核心模型
-> 契约边界
-> 最小闭环
-> Debug
-> Build
-> 验收
-> 冻结
-> 被下游消费
```

本原则的目标不是增加开发复杂度，而是保证项目在长期演进中始终保持清晰、稳定、可验证、可扩展。
